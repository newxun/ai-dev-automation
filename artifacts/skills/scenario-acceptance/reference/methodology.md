# Methodology：综合检查链

> 由 `SKILL.md` 引用。进入「综合检查链」步骤时参考，按当前任务实际风险取用，不必对每一项都做同等深度的调查。

## 追踪关系

建立并在报告中体现如下追踪关系，任一环节缺失都要显式标注，不能跳过后继续：

```text
原始需求 → 任务职责与边界 → 实际代码修改 → 测试证据 → 代码 Review 结论 → 验收结论
```

## 1. 需求一致性

- 确认本次验收使用的需求版本与开发就绪阶段采用的是否一致；开发期间需求发生变化时，检查变化是否已经进入任务契约（开发就绪任务报告的「目标、边界与验收」）。
- 核对是否遗漏或误解原始听记/需求文档中的关键要求，不能只对照任务摘要——摘要可能已经丢失细节。
- 需求存在歧义或多个版本冲突时标记 `[证据冲突]`，不擅自选择其中一个。

## 2. 职责覆盖

- 把每一项需求映射到实际实现和验证证据（代码差异中的具体位置 + 测试报告中的具体测试项）。
- 发现某项需求没有对应实现或证据时，标记为阻塞验收，不能因为「大部分需求已完成」而忽略。

## 3. 越界修改

- 检查代码差异中是否存在无需求依据的行为变化、重构或范围扩大。
- 越界修改本身不一定是问题，但必须有清晰记录：是否经过确认、是否增加了额外回归风险、是否应该拆分到单独任务。
- 未经确认的越界修改记为需要业务或用户决策，不能自行认定「顺手做了也无妨」。

## 4. 功能证据

- 读取 Testing Skill 报告，确认必要测试是否通过，测试所用代码版本是否与最终交付版本一致。
- 测试报告存在阻断性失败、关键缺口或版本不一致时，验收结论不能是「通过」。
- 不重新运行测试；如确有必要复核个别关键结果，明确说明是复核而不是重新做一遍完整测试。

## 5. 代码质量（消费既有 Review 结论）

- 复用现有代码 Review 能力（当前仓库是 [`ai-assisted-code-review`](../../../workflows/ai-assisted-code-review/README.md) 工作流 + 检查清单，不是结构化 Skill）的结论，确认其中标记的阻塞问题是否已处理。
- Review 结论可能以 PR 评论、勾选后的检查清单、或用户转述等任意形式存在；缺失、无法访问或明显是很久之前的版本时，在报告中记为证据缺口，按任务风险决定是否阻断验收，而不是直接判「无法验收」或假装已经审查过。
- 不重新做一遍代码质量判断；如发现 Review 结论明显与当前代码不符（例如引用的文件已经改变），标记 `[证据冲突]` 并说明。

## 6. 项目全局一致性

- 检查修改是否破坏业务、架构、数据、权限或兼容边界；参考开发就绪阶段的项目基线（`docs/development-readiness/<timestamp>-baseline.md`）。
- 项目基线本身可能过期，发现基线记录的事实与当前代码不符时标记 `[证据冲突]`，不能只信旧基线。

## 7. 回归风险

- 检查直接受影响模块之外，是否存在共享代码、公共组件或相似实现受到间接影响。
- 关注开发就绪报告中记录的历史负债、高风险区域是否被本次修改触及。
- 无法验证的间接影响标记 `[未确认]`，不能凭直觉断言「应该没问题」。

## 8. 知识回流

- 判断本次开发是否改变了项目事实（新增约定、废弃旧路径、修正了过期文档）。
- 不直接修改 development-readiness 的基线文件（那由该 Skill 自己的会话维护）；而是在验收报告中列出「建议更新到项目基线的内容」，供下一次 development-readiness 会话或用户合并。

## 结论判定参考

- 需求一致性、职责覆盖、功能证据均满足，代码质量无未处理阻塞项，全局一致性和回归风险无未接受的高风险 → 通过。
- 存在已明确、可接受、有责任人的限制 → 有条件通过（见 `protocols.md` 的记录要求）。
- 存在明确的实现、测试或代码质量缺陷 → 需要修复。
- 需求版本、业务口径或越界合理性无法自行裁决 → 需求待确认。
- 关键资料、环境或证据缺失，无法形成可靠判断 → 无法验收。
