# Methodology：测试选型、失败分类与成本控制

> 由 `SKILL.md` 引用。会话开始与选择测试组合时参考。

## 输入完整性检查

开始执行前确认以下输入均存在且指向同一份代码：

- 开发就绪任务报告中的验收条件、验证矩阵、回归范围。
- 最终代码版本（分支、Commit、工作树状态）。
- 环境与数据前提（能否本地复现、是否需要测试凭据）。

任一输入缺失、版本对不上（例如测试报告引用的 Commit 与当前工作树不一致），先在报告「输入核对」小节记录缺口并询问，不能假装齐全后继续执行；风险明显较高的任务应把缺口标记为验收阻断。

## 测试选型

从验收标准和实际修改类型推导最小充分组合，不因为「测试要全」就机械跑遍所有 build/test/lint：

1. 优先复用项目已有的单元、集成、接口测试；先确认它们确实覆盖本次修改路径，而不是只看测试文件名称相关。
2. 修改涉及数据库、状态机、权限或跨服务调用时，检查是否有对应集成/接口测试；缺失时在报告标注缺口，视风险决定是否需要补充手工验证。
3. 只有验收标准明确要求或修改直接影响用户可见页面/流程时，才进入 `browser-functional-testing.md`。
4. 只有存在视觉需求或视觉回归风险（布局、样式、响应式、截图差异）时，才进入 `visual-testing.md`；不作为所有任务的固定步骤。
5. 任务只涉及后端逻辑、CLI 或库时，不启动浏览器，不制造与任务无关的验证步骤。

## 失败分类

记录原始命令、退出码、脱敏错误或日志位置、已尝试方法及结果、排除依据，归入以下类别之一：

- **实现问题**：代码逻辑与验收标准不符。
- **测试自身问题**：断言、夹具或测试数据有误；记录但不擅自修改，交给用户或 Coding Agent 确认。
- **环境或数据问题**：本机、依赖、测试数据或权限导致无法验证，不代表实现有问题。
- **业务预期未知**：无法判断某个结果是否符合预期，需人工确认。

无新增证据不重复同类尝试，不把「本机偶然跑通」当作已解释的根因。

## 成本控制

浏览器与视觉分析较耗上下文，采用定向验证：

1. 从验收标准提取少量关键用户路径，不自由探索。
2. 优先用确定性脚本执行操作和断言，减少对视觉模型的依赖。
3. 只在关键状态采集截图，不逐帧记录。
4. 正常路径保存简洁证据；出现失败后再针对失败点深入分析。
5. 不默认对视频逐帧分析，不做无目标的自由浏览。

## 数据与安全

「真实数据」不能默认等于生产数据。优先级：

1. 可复现的测试数据。
2. 测试或预发布环境中的代表性数据。
3. 经明确授权的生产只读抽查。

修改、删除、发送消息、支付、审批等具有业务副作用的操作必须有明确授权和隔离措施，走 `protocols.md` 的确认协议。测试证据不得泄露凭据、个人信息或敏感业务数据；写入报告前脱敏。

## 报告内容要求

测试报告至少包含：被测代码版本和工作树状态；环境与数据前提；验收标准到测试项的对应关系；执行命令或可复现步骤；通过/失败/跳过/无法执行/需人工确认的结果；日志、截图等证据位置；发现的问题和剩余测试缺口。测试未通过或关键测试缺失时标记为验收阻断，不由本 Skill 自行降低验收标准或视为“基本能用”。
