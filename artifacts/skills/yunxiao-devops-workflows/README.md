# Yunxiao DevOps Workflows

## Problem

云效（阿里云 Yunxiao）官方 MCP Server（[alibabacloud-devops-mcp-server](https://github.com/aliyun/alibabacloud-devops-mcp-server)，参见[官方使用说明](https://help.aliyun.com/zh/yunxiao/developer-reference/cloud-effect-mcp-tool-instructions)）已经支持用自然语言直接调用云效的组织管理、代码管理 Codeup、项目协作 Projex、流水线 Flow、制品仓库 Packages、应用交付 AppStack、测试管理 Testhub 共 8 类、194 个工具。

但接入 MCP 本身不等于形成可靠工作流：194 个工具没有内置「先查什么再查什么」的顺序、没有统一的组织/项目 ID 解析约定、也没有区分"随便读"和"必须先确认再写"的边界。缺少这层规范时，日常最容易反复发生的三类真实场景仍然低效或有风险：

1. 开发需求前，需要把云效的需求描述、字段、评论、变更历史、关联合并请求拼成一份完整的任务上下文，容易漏看藏在自定义字段或活动历史里的关键信息。
2. 部署/发布时，需要发起流水线、定位失败 Job 和日志、区分是代码问题还是环境/审批问题、必要时看合并冲突——如果没有确认边界，容易在没弄清楚原因前就重复触发生产相关的动作。
3. 需求拆任务、登记和统计工时是高频重复操作，纯手工在网页里创建子任务、逐条填工时、导出统计非常繁琐，但拆分方案和工时数值又不能完全交给 AI 自主决定。

## Goal

在云效 MCP 之上提供一层可复用的工作流规范，覆盖三个真实场景：

1. **开发前同步**：把工作项信息转成可执行的任务简报。
2. **部署协助**：把流水线/发布单的状态和日志转成可执行的修复线索，高风险动作强制确认。
3. **拆任务与工时**：协助拆分子任务、登记工时、按时间窗口统计，关键决策仍由用户确认。

不新增 API 能力，只解决"按什么顺序调用已有工具""哪些结论需要先确认再执行"。

## Use Cases

- 开发前想知道完整背景：查我参与的所有需求（或按编号/关键字定位某条需求），连同挂在需求下、责任人为我的任务，一并拉出需求和任务上的全部评论，汇总成任务简报。
- 临时接手一个云效上的需求，开发前想知道完整背景（需求、任务、评论、历史合并请求）。
- 部署失败后，想让 AI 帮忙定位失败的流水线 Job、拉日志、判断是代码问题还是环境/审批问题。
- 合并请求有冲突，想先看清楚双方改动再决定合并策略，而不是被动跳转到网页处理。
- 一个需求需要拆成多个子任务分给团队成员，且需要登记预计/实际工时。
- 需要按周/迭代统计个人或团队的工时，减少手动导出和汇总。

## Not For

- 自动触发生产发布、跳过审批、或在没有明确授权的情况下连续重跑流水线。
- 替用户决定任务拆分粒度、负责人分配或工时数值。
- 在未展示双方差异并征得确认的情况下"自动解决"代码合并冲突。
- 替代云效原生的报表/仪表盘——本 Skill 只做明细查询和本地聚合，不保证与官方报表口径一致。

## 形态说明

三条工作流都是**人在环、可能跨会话**的真实研发场景，且共享同一套身份解析和写操作安全模型，因此组织成一个 **Skill**（而不是三个独立 Skill 或一个 Subagent）：不像 `development-readiness` 那样是顺序推进的三个阶段，而是三个独立入口，按用户当前意图选择读入对应 reference，避免一次性加载全部内容占用上下文。

高风险、非交互、边界明确的子任务（例如单纯"把这份失败日志的报错栈整理归类"）仍可以在需要时派发给一个专项子 Agent，但组织/项目上下文解析、写操作确认、任务拆分决策等人在环环节应留在主对话，不整体塞进 Subagent。

## Usage

### Claude Code

作为 Agent Skill 使用：将本目录放到 Claude Code 能发现 Skill 的位置，`SKILL.md` 的 frontmatter `description` 用于自动触发。使用前需已按[官方文档](https://help.aliyun.com/zh/yunxiao/developer-reference/cloud-effect-mcp-tool-instructions)接入云效 MCP（远程托管或 stdio），并获取具备所需读写权限的个人访问令牌。

### Codex 或其他工具

将 [`SKILL.md`](SKILL.md) 作为主 Agent 指令使用，需要细节时按其中指针读取 `reference/` 下对应文件。确保已接入云效 MCP，并按将要执行的工作流通过 `toolsets` 参数只加载需要的工具集，减少上下文占用。

### Suggested Start

```text
我已经接入云效 MCP。请使用 Yunxiao DevOps Workflows 帮我查一下我参与的所有需求，连同挂在需求下责任人为我的任务，把需求和任务上的所有评论都拉出来，汇总成任务简报。
```

```text
我已经接入云效 MCP。请使用 Yunxiao DevOps Workflows 帮我在开发前同步工作项 #<id> 的需求、任务和评论，输出一份任务简报。
```

```text
昨晚的发布流水线 <流水线名/ID> 失败了，请用 Yunxiao DevOps Workflows 帮我定位失败的 Job、拉日志并判断失败原因；除非我明确同意，不要自动重跑或触发新的部署。
```

```text
请用 Yunxiao DevOps Workflows 帮我把需求 #<id> 拆成子任务草案，我确认后再帮我创建并登记预计工时。
```

## Inputs

必需：

- 已接入且可用的云效 MCP（远程托管或 stdio），具备所需 toolset 的读写权限。

可选：

- 具体的组织/项目/工作项/流水线/仓库 ID 或链接（没有时会先用只读工具检索）。
- 团队特有的字段命名、工作流状态、工时登记规则等背景信息。
- 明确禁止执行的动作（例如"不要碰生产流水线"）。

## Expected Behavior

Agent 应：

- 只读工具自由调用，写操作按协作类/结构类/高风险类分级确认。
- 高风险动作（流水线触发、发布单/环境操作、审批通过或拒绝）逐次征得明确同意，不做隐式授权扩展。
- 代码合并冲突只整理差异证据，合并策略交给用户或编码环节决定。
- 任务拆分方案和工时数值在写入前逐条展示确认。
- 明确标注信息来源（工具名 + 关键 ID）和查询时间，不把明细数据包装成官方报表。

Agent 不应：

- 因为对话提到"部署""发布"就默认获得连续触发流水线或发布单操作的授权。
- 替用户决定任务拆分粒度、负责人或工时数值。
- 把单条评论或单次活动记录当成最终结论，而忽略更完整的字段/工作流/历史证据。

## Human Confirmation

- 需求验收标准的解读、是否存在系统外团队共识。
- 任何会通知协作方的写操作内容（评论文案、状态变更）。
- 任务拆分方案（数量、边界、负责人）。
- 工时登记的日期、数值、关联工作项，以及统计口径（时间范围、是否含未关闭任务）。
- 任何触达生产环境、审批流程或对外发布的动作及其回滚方式。

## Limitations

- 依赖云效 MCP 已正确接入且令牌具备相应权限；权限不足时对应工具会调用失败，需要用户补充授权。
- `list_current_user_effort_records` 等工时接口存在时间跨度限制（不超过 6 个月），长跨度统计需要分段查询再合并。
- MCP 只提供明细数据，不提供聚合报表，本地聚合逻辑需要和用户对齐口径，不保证与云效官方统计完全一致。
- 194 个工具随官方版本可能新增/调整，本 Skill 引用的工具名以 [alibabacloud-devops-mcp-server](https://github.com/aliyun/alibabacloud-devops-mcp-server) README 为准，需要定期核对是否有变化。

## Roadmap

- 视真实使用情况补充测试管理（Testhub）和制品仓库（Packages）相关的工作流。
- 收集实际使用中遇到的字段/工作流命名差异，沉淀为可复用的组织级约定清单。
- 若与 `development-readiness` 的任务就绪阶段配合使用产生固定模式，评估是否需要显式的衔接说明或共享模板。
