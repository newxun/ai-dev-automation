# 开发前同步：需求 / 任务 / 评论

> 由 `SKILL.md` 引用。目标：把「我要看的需求」以及「分配给我、挂在这条需求下的任务」，连同两者身上的**全部**评论，汇总成一份可执行的任务简报，减少「代码写完才发现漏看了一条评论」的返工。

## 定位需求：三种触发方式

按用户这次实际说的话选一种，不要三种都跑一遍：

1. **我参与的所有需求**（列表模式，可能返回多条）：
   - 云效工作项有原生的 `participants`（参与人）字段，但 `search_workitems` 顶层参数只暴露了 `creator` / `assignedTo` 两个可以直接传 `"self"` 简写的字段，没有暴露 `participants`。要按参与人过滤，需要：
     1. `get_current_user` 拿到当前用户的真实 userId（`"self"` 简写只对 `creator` / `assignedTo` 生效，`advancedConditions` 里必须传真实 ID）。
     2. 用 `advancedConditions` 传原始过滤条件（JSON 字符串）：
        `{"conditionGroups":[[{"fieldIdentifier":"participants","operator":"CONTAINS","value":["<userId>"],"toValue":null,"className":"user","format":"list"}]]}`
     3. 配合 `category=Req`、`spaceId=<项目ID>` 一起传给 `search_workitems`。
   - 如果用户说的"参与"实际是指「责任人是我」（更常见、更省一次工具调用），直接 `search_workitems(category=Req, spaceId=..., assignedTo="self")` 即可，不需要解析真实用户 ID。
   - **"参与者"具体指哪个字段，第一次遇到时和用户确认一次**（责任人 / 原生参与人字段 / 团队自定义的其他字段），不要自己假设；确认后同会话内复用，不用每次重新问。
   - 默认按 `status` 过滤掉已关闭/已验收的需求，除非用户明确要看全部历史需求（否则一次性拉出全量历史需求信息噪音很大）。

2. **按编号查询**：已有 ID/链接直接 `get_work_item(workItemId=<id>)`，最精确，优先使用。

3. **按关键字查询**：`search_workitems(category=Req, spaceId=..., subjectDescription=<关键字>)`（标题+描述都匹配，召回更全）；命中太多时改用 `subject=<关键字>`（仅标题，更精确）收窄。命中多条时，把候选列表（标题 + ID + 状态）先展示给用户确认是哪一条/哪几条，不要自己猜一条就往下走。

以上任一模式的结果都可能是 1 条或多条需求；后续步骤对每一条需求重复执行。

## 拉取责任人为我的任务

对每条已定位的需求：

1. `search_workitems(category=Task, spaceId=<项目ID>, assignedTo="self")`，拿到当前用户名下的全部任务（同样可以直接用 `"self"`，不需要解析真实 ID）。
2. 用返回结果里的 `parentId`（父工作项 ID）字段和当前需求的 ID 做本地过滤，筛出真正挂在这条需求下的任务。**`parentId` 是否在列表接口返回体里直接给出，不同数据/版本可能有差异**——如果 `search_workitems` 返回体没带 `parentId`，对候选任务逐个 `get_work_item(workItemId=<taskId>)` 补齐这个字段再过滤，不要跳过校验直接把"我名下所有任务"当成"这条需求下我的任务"。
3. 过滤后如果某条需求下没有任何任务命中，在简报里明确写"该需求下暂无分配给我的任务"，不要静默跳过——用户可能正想借此发现"漏派任务"的情况。
4. 如果用户明确说的是"我名下所有任务"而不是"这条需求下的任务"，跳过第 2 步的归属过滤，直接用第 1 步的全量结果，并在简报里注明这些任务未按需求归类。

## 拉取评论（需求层 + 任务层，两层都要）

- 对每条需求：`list_work_item_comments(workItemId=<需求ID>)`。
- 对每条命中的任务：`list_work_item_comments(workItemId=<任务ID>)`。
- 默认 `perPage=20`；返回条数达到 `perPage` 时翻页继续拉，直到拿完，不要因为第一页看着评论不多就断定"没有更多评论"。
- 评论之外，需求的范围/验收标准也可能是通过改字段而不是发评论变化的，需要更完整背景时再按需读取 `list_workitem_activities`（活动历史）——默认不强制拉，避免每次都做一次全量历史扫描。

## 汇总成任务简报

按「需求」分组输出，每条需求包含：

- 需求标题 / ID / 当前状态 / 所属迭代或版本 / 责任人。
- 需求描述与验收标准（来自 `get_work_item` 详情；必要时用 `get_work_item_type_field_config` 核对验收标准具体存在哪个字段，不同项目命名可能不同，不要靠猜）。
- 该需求的全部评论（时间、作者、内容，按时间正序）。
- 挂在该需求下、责任人为我的任务清单：每条任务的标题 / ID / 状态 / 该任务的全部评论。
- 未解决的疑问或风险点（评论里悬而未决的问题、状态和验收标准对不上的地方）。

结尾统一标注："以上信息来自云效工作项 <需求ID列表>，截至 <查询时间>"，避免被当成实时权威数据长期引用。

## 人工确认点

- "参与者"具体指哪个字段（责任人 / 原生参与人字段 / 其他自定义字段），第一次使用时和用户对齐一次，同会话内复用。
- 需求验收标准的解读是否准确、是否存在系统外的团队口头共识——这类判断必须由用户确认，不能靠 Agent 脑补。
- 如果需要把"已看到需求、开始开发"这类状态同步回云效（`create_work_item_comment` 或 `update_work_item` 改状态），必须先把文案/目标状态展示给用户，因为这会通知需求相关方，写错会造成误解。
- 工作项字段命名和状态机因组织/项目而异，第一次接触某个项目空间时，把 `get_work_item_type_field_config` 和 `get_work_item_workflow` 的关键结论记下来，同会话内复用，不要每个工作项都重新问一遍用户"你们的状态是什么意思"。

## 常见误区

- 把"我名下所有任务"直接当成"这条需求下我的任务"，没有用 `parentId` 做归属校验。
- 只读 `get_work_item` 的描述字段就认为拿到了全部需求信息——描述之外的自定义字段、评论、活动历史经常才是最新结论所在。
- 只拉需求的评论、漏掉任务本身的评论（或反过来）——两层评论都要覆盖，是本工作流和"只查一个工作项详情"的关键区别。
- 关键字查询命中多条时不和用户确认就自己选一条处理。
- 需求范围不清晰时，Agent 自己猜测边界后就直接开始建议实现方案，而不是先把"未解决的疑问"列出来交给用户。
