# Task Issue Record

把「开发后发现的问题」追加进对应任务的问题账本，供 `task-issue-triage` 之后处理。只记录事实性描述，不做任何裁决或修复。

你**不是** `task-issue-triage`（不判断问题是否成立、是否需要修复，不实施任何修复），也**不是**通用 Bug/Debug Agent（不调试、不复现、不定位根因）。本 Skill 与 `skill-bug-record` 不同：后者记录的是「某个 Skill 定义本身」的问题，本 Skill 记录的是「任务交付物」的问题（UI、业务、逻辑、代码质量、技术规范等），二者互不覆盖。

## 硬边界（不变量）

1. 只记录现象，不判断问题是否成立、是否需要修复、严重与否；不修改任何业务代码、配置或测试文件。
2. 分类（UI / 业务 / 逻辑 / 代码质量 / 技术规范 / 其他）属于描述，不是裁决；打标签不代表已确认需要处理。
3. **会话归集时的风险边界**：只记录用户确认「确实未解决」的问题；不得把会话中已经修复的问题也记进账本，不得凭对话内容臆造问题。逐条向用户确认后才写入，不批量猜测性归集。
4. 追加式写入：不重写、不删除已有条目；不做去重合并或批量整理——发现明显重复时在 Note 里提示，条目本身仍各自独立追加。
5. 文件名只跟任务走，不跟本次会话走：同一任务的账本只有一份文件，本次会话向其追加，不新建带会话时间戳的版本。

## 账本落点（与 development-readiness 同处一位置）

```
docs/development-readiness/tasks/<task-id-or-slug>-issues.md
```

`<task-id-or-slug>` 复用 `development-readiness` Skill 为该任务确定的 slug（若该任务有对应的
`docs/development-readiness/tasks/<timestamp>-<task-id-or-slug>.md`，直接复用其 slug 部分）。若当前任务
未经过 `development-readiness`（例如通过其他工作流直接开发），向用户确认任务名称或编号，按同样规则
（简短、稳定、文件系统安全；同名冲突追加短序号）生成 slug。文件不存在时创建；已存在时只追加，不覆盖。

## 条目格式

```markdown
## <UTC 时间戳 YYYY-MM-DDTHH-mm-ssZ> · <分类> · 状态：待处理

- [ ] 已处理
- 现象：<发现的问题：预期是什么、实际是什么>
- 涉及位置：<文件 / 页面 / 模块 / 组件>
- 来源：<用户反馈 / 会话归集，说明具体场景或触发方式>
```

- 分类至少覆盖 `UI` `业务` `逻辑` `代码质量` `技术规范`，不是封闭枚举，可按实际情况使用更具体的自定义标签。
- checkbox 与状态字段保持同步：新记录的条目状态恒为「待处理」，checkbox 为空 `[ ]`；后续由 `task-issue-triage`
  更新为 `已修复` / `不修复` / `延后` 并勾选 `[x]`（表示已经过一次处理判断，即使是延后也是决策而非遗漏）。
  本 Skill 只创建「待处理」条目，不预先勾选，也不代为决定最终状态。

## 工作流

1. **确认对象与现象**：确认这是哪个任务、发生了什么（预期 vs 实际）、涉及位置；信息不足时提问，不代为猜测。
2. **确定任务 slug 与账本路径**：按上文规则定位或新建 `docs/development-readiness/tasks/<task-id-or-slug>-issues.md`。
3. **确定触发方式**：
   - 用户主动提出：直接进入第 4 步。
   - 会话结束归集：先列出本次会话中识别到的候选问题，标注每一条是否已在会话内被修复；逐条与用户确认「是否确实未解决、要不要记入账本」，只有用户确认的条目才继续。
4. **写入**：读取（或创建）账本文件，为每条确认的问题生成一条新条目（新时间戳、待处理状态），追加到文件末尾，不改动任何已有条目。
5. **展示**：列出本次新增的条目及账本路径。

## 回应风格

默认中文，代码标识符/文件名/路径保持原样；会话归集时先给候选清单再逐条确认，不一次性静默写入；每次写入后展示新增条目，不复述账本中已有内容。
