# Methodology：来源路由、浏览器取证与修复循环

> 由 `SKILL.md` 按需读取。用于执行设计源解析、关键状态截图、独立视觉诊断和自动修复。

## 1. 输入与来源解析

先记录当前任务 slug、分支、Commit、工作树、需求来源和设计来源。来源按顺序解析：

1. 用户在本轮明确指定的链接或图片。
2. 当前消息和附件中的蓝湖域名链接、设计稿图片。
3. 文件名匹配当前任务 slug 的最新 `development-readiness` 任务报告。
4. 任务报告「任务基线」中的设计稿链接/稿件标识，以及它明确引用的 `raw/` 文件。

找到更高优先级来源后即停止向下自动发现。只有用户明确要求组合多个来源，或同一优先级本身同时
提供链接和图片时才进入多来源模式；不得把用户显式指定的新链接与 `raw/` 中旧图片自动合并。

第三步必须匹配当前任务；不能因为某份报告时间最新就把另一个任务的设计稿拿来使用。无法确定
任务 slug、匹配到多个候选或报告引用已失效时，只问一个会改变路由结果的问题。

### 蓝湖来源

1. 发现运行环境可用的蓝湖 MCP 能力，读取目标画板的结构化信息和原始预览/导出画面。
2. 记录链接、稿件或画板标识、采集时间；能取得版本或更新时间时一并记录。
3. MCP 返回体过大时使用其原生筛选能力缩小到任务相关画板，不先总结全稿再从总结中比较。
4. 若原始数据需要落盘，保留原始返回或工具导出；报告只引用，不把自然语言转译升级为设计基准。
5. MCP 无法返回可比较画面时，可浏览器打开蓝湖作为降级。固定缩放、隐藏工具栏/标注层并记录降级。

### 图片来源

直接使用用户提供或任务材料引用的原图。允许去除浏览器外框、无关留白和明确的批注层，但不得
重绘、补全或生成“更清晰”的替代设计。先从图片列出可观察的页面区域、元素、相对方位、布局层级
和明显样式，不能从单张图推断未展示的交互或响应式状态。

### 多来源

蓝湖链接和图片同时存在时：

- 蓝湖结构数据用于元素、层级、尺寸、样式核对。
- 图片用于最终视觉基准。
- 画板版本、元素有无或布局明显冲突时同时保留双方，不静默选择。

## 2. 关键状态矩阵

每个状态一行：

| 状态 | 设计画面 | 实现 URL | 准备步骤 | 视口 | 必须比较的区域 |
| --- | --- | --- | --- | --- | --- |

选择最小充分集合：

- 默认加载完成状态。
- 本任务直接修改的弹窗、抽屉、菜单、选中态或空状态。
- 需求或设计明确提供的权限、错误或数据状态。
- 本任务明确影响的桌面/移动断点。

不自动添加设计稿未覆盖的状态，不为了“更全面”遍历所有页面和断点。

## 3. 浏览器取证

### 环境固定

- 使用设计画板对应的视口；记录 viewport、DPR 和页面缩放。
- 固定主题、语言、字体加载、测试数据和登录身份。
- 关闭动画与光标闪烁；等待字体、图片和关键请求稳定。
- 动态时间、随机内容或轮播无法冻结时，标记并从视觉判断中排除对应区域。
- 记录最终 URL、Console/Page Error 和失败请求，帮助识别“没有正确渲染”而非设计偏差。

### 截图规则

- 初始轮与最终轮：每个关键状态保存完整截图。
- 中间轮：可以只截本轮修改区域，但不能用局部截图替代最终全画面。
- 设计与实现保持相同裁切范围；不得通过不同缩放让两者看似一致。
- 截图含凭据、个人信息或敏感业务数据时，先使用安全测试数据；必要脱敏不得遮住待比较区域。

## 4. 独立视觉 Agent 契约

派发一个新的、具备图像理解能力的独立上下文。输入只包含：

1. 设计画面和实现截图的文件路径或附件。
2. 状态名称、视口、裁切说明。
3. 蓝湖结构核对中与该画面直接相关的事实。
4. 已由用户确认接受的偏差。
5. 下述固定输出格式。

```markdown
| 区域 | 设计预期 | 实现现状 | 类型 | 严重程度 | 证据 | 置信度 |
| --- | --- | --- | --- | --- | --- | --- |
```

类型：缺失 / 多余 / 位置 / 布局 / 层级 / 尺寸 / 样式 / 无法判断。

严重程度：

- 阻碍使用：遮挡关键操作或导致页面不可用。
- 主要偏差：结构、主要方位、核心元素或视觉层级明显不一致。
- 次要偏差：不影响主要构图的局部样式问题。

要求诊断者先独立观察再输出，不向其提供实现者的辩护或“预计已经修好”的结论。禁止仅给
“整体一致、细节略有差异”之类不可执行总结；每个问题必须定位到区域并同时描述预期与实际。

## 5. 合并与修复

先处理结构和主要方位，再处理局部样式：

1. 合并蓝湖结构检查与视觉观察，用页面/状态/区域去重。
2. 标记来源冲突、低置信度观察和已接受偏差；这些不进入自动修改队列。
3. 将确定问题映射到 DOM、组件、样式或 token。
4. 优先修改最小局部范围；只有证据表明根因位于共享组件/token 时才修改共享位置。
5. 每批修改后运行受影响功能的最小测试，再进入浏览器复查。

可以直接修改：CSS、token、字体、颜色、间距、尺寸、对齐和不改变业务语义的表现层结构。设计稿
明确展示了同一业务入口且只需将现有入口移动到该明确位置时，属于 UI 呈现修复，可直接执行。

先确认：有业务行为的入口增删；设计稿未展示该入口时为它发明新位置；交互条件变化、共享组件公共
API、大范围重构、来源冲突，以及可能影响任务外页面但无法验证的修改。

“需求要求功能存在、设计稿未展示”不是自动寻找新位置的授权。它是行为与呈现无法同时满足的冲突，
必须将当前实现、需求条款和设计证据一起交给用户裁决。

## 6. 轮次与完成

每轮记录：计划修复项、实际文件、功能测试、重新截图、独立复查结果和剩余问题。

- 第 1–2 轮可针对确定问题继续修复。
- 第 3 轮完成后无论结果如何都停止自动循环。
- 任何轮次出现来源冲突、独立诊断结论反复、运行环境失稳或修改越界，立即停止相关项。

最终独立复查必须使用新上下文和最终代码截图。完成意味着主要偏差清零或有明确处置；不意味着
像素级一致，也不意味着最终 UI/业务验收通过。
