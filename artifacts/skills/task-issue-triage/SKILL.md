# Task Issue Triage

读取某个任务问题账本中「待处理」的条目，逐条判断是否需要修复，实施修复或给出理由，并立即回写状态。

你**不是** `task-issue-record`（不负责发现和记录新问题，只处理已有条目；发现记录之外的新问题时改用
`task-issue-record` 单独记录，不顺手混进本次处理）。本 Skill 与 `skill-bug-triage` 不同：后者处理的是
「某个 Skill 定义本身」的问题，本 Skill 处理的是「任务交付物」的问题（代码、UI、业务、文档等），修复
目标是仓库中的实际文件而不是 Skill 定义。

## 硬边界（不变量）

1. 一次处理可以只覆盖部分条目（某个分类、某几条），其余保持「待处理」；不强制一次处理完整份账本。
2. 每处理完一条立即回写该条目状态、checkbox 与处理结果，不批量攒到最后统一更新。
3. 涉及影响面较大的修改（跨模块、影响公共组件/接口、可能影响其他任务）时，先说明修复方案（改动范围、
   预期影响、验证方式）并等待确认，再实施；小范围、无歧义的修复可以直接实施。
4. 不改动条目已记录的原始字段（现象、涉及位置、来源、发现时间）；处理结果只以追加形式写在该条目内。
5. 找不到涉及位置对应的文件、或问题描述已明显不再适用（例如相关代码已被后续改动移除）时，标记
   `不修复` 并说明理由，不强行猜测目标文件或代为改写现象描述。
6. 永不删除已有条目；`已修复` / `不修复` / `延后` 都是最终会被追加说明的状态，不静默跳过未处理的条目。

## 状态与回写

条目状态 ∈ `待处理` `已修复` `不修复` `延后`：

- `已修复`：已实施修复，说明改了什么、在哪个文件、如何验证。
- `不修复`：判断后确认不需要修复，说明理由（例如已被后续改动覆盖、是预期行为、优先级不足且经用户确认）。
- `延后`：确认需要处理但本次不适合立即修（例如影响面需要专项排期），说明延后理由和建议的后续处理方式；
  延后不等于遗漏，仍需 checkbox 打勾，未来可基于「延后」原因重新拿出来评估。

回写时更新条目标题的状态、把 checkbox 改为 `[x]`，并在条目末尾追加：

```markdown
- 处理结果：<已修复：改了什么/在哪个文件/如何验证；不修复：理由；延后：理由与建议后续动作>
- 处理时间：<UTC 时间戳>
```

## 账本落点

```
docs/development-readiness/tasks/<task-id-or-slug>-issues.md
```

与 `task-issue-record` 使用同一份文件、同一套 `task-id-or-slug` 规则。

## 工作流

1. **定位账本**：确认任务标识，读取对应的 `<task-id-or-slug>-issues.md`；文件不存在或没有任何条目时
   说明情况并停止，不臆造条目。
2. **列出待处理条目**：按分类分组列出所有状态为「待处理」的条目。
3. **确认本次范围**：默认处理全部待处理条目；用户可指定只处理某个分类或具体几条，其余留待下次。
4. **逐条处理**：定位涉及位置，判断问题是否成立、是否需要修复；影响面较大时先给出方案等待确认；决定
   `已修复` / `不修复` / `延后`。
5. **立即回写**：处理完一条立即更新该条目状态、checkbox 与处理结果，再处理下一条。
6. **汇总**：说明本次处理了几条、修了什么、不修的理由、延后的原因，以及账本中还剩多少条「待处理」。

## 回应风格

默认中文，代码标识符/文件名/路径保持原样；先给本次处理范围与结论汇总，再给必要证据；影响面较大的
修复先展示方案再动手，不先改后解释；每处理完一条立即展示回写结果，不等到最后才批量汇报。
