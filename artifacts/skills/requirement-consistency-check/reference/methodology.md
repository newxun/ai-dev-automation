# Methodology: 三阶段核对维度、严重度判定与材料获取

> 由 `SKILL.md` 引用。按当前阶段取用，不需要一次读完。

## Phase 1：需求文档自查（综合审查，最重要）

这是整个 Skill 中最重要的阶段。**不是关键词扫描或几条规则打勾**，而是通读全文，带着"同一件事在别处是怎么说的"这个问题跨章节交叉核对。核心检查维度：

1. **术语/字段/实体定义一致性**：同一个名词（功能名、字段名、状态名、角色名、枚举值）在不同章节的定义、取值范围、含义是否一致。常见于文档反复修订后，早期章节的旧定义没有跟着后期修订同步。
2. **逻辑完备性与互斥性**：条件分支是否覆盖完整（例如只写了成功路径，没写异常/边界情况）；是否存在两个条件被要求同时满足但实际互斥的情况；是否存在遗漏的前置条件。
3. **版本残留与同步痕迹**：文档中是否存在两种相互矛盾的方案描述并存（新方案已经写入，但旧方案的相关段落没有删除或更新）；更新日志/版本说明与正文是否对应；是否有"沿用上一版逻辑"之类未处理的过渡性表述。这类问题是用户描述的核心痛点之一——需求改了一半没同步。
4. **举例与规则一致性**：文中给出的示例、表格数据、截图说明是否符合前文定义的规则；示例本身经常是最先被遗忘更新的部分。
5. **AI 生成痕迹与完整性缺口**：是否存在未替换的占位符（TBD、待补充、xxx、示例文字）；是否存在内容空洞但看起来完整的重复表述；是否存在结论缺少前提支撑的逻辑跳跃——这些是 AI 生成后未经人工校对的典型信号。
6. **内部引用一致性**：章节间的交叉引用、编号、附图/流程图与文字描述是否对应；引用的章节号或术语是否随文档调整同步更新。

### 严重度判定示例

- **阻断级**：同一份文档不同章节对同一功能的核心规则给出方向性互斥的描述（例如"满足条件 A 才能提交"，后文又写"无需满足条件 A 即可提交"），且无法从上下文判断哪个是最新有效版本。
- **需要澄清**：文档存在占位符/待补充内容，或表述模糊、存在潜在歧义但不构成直接矛盾，需要作者确认真实意图。
- **轻微**：措辞、顺序、格式、非核心信息的出入，不影响理解和后续实现。

## Phase 2：需求文档 vs 原型图

聚焦**功能覆盖与交互流程**，明确**不比较原型图的视觉布局**——原型稿（Axure / PRD 内的示意图）上的元素位置通常是随手摆放的，不作为布局依据；本阶段只关心"流程和功能对不对得上"，不关心"画得好不好看、摆得对不对"。

### 检查维度

1. **功能/页面覆盖**：需求文档提到的每个功能点、页面、状态，能否在原型图中找到对应载体。
2. **反向覆盖**：原型图中出现但需求文档未提及的流程、页面或交互——可能是需求描述遗漏，也可能是原型冗余，两种可能都要列出，不预设结论。
3. **流程顺序与分支逻辑**：关键操作步骤的先后顺序、分支条件（例如"选择 A 后才出现 B 选项"）在两份材料中是否一致。
4. **触发条件与结果的一致性**：原型图中交互产生的结果（页面跳转去向、提示信息、状态变化）与需求文档描述的预期结果是否一致。

### 严重度判定示例

- **阻断级**：需求文档明确要求的核心功能，在原型图中完全找不到可以承载它的流程或页面，导致按原型图理解会遗漏该功能。
- **需要澄清**：流程顺序或分支条件存在出入，无法判断是原型图表达有误还是需求文档描述不清。
- **轻微**：非核心、辅助性的交互细节存在出入，不影响核心流程理解。

## Phase 3：需求文档+原型图 vs 设计稿

复用 `development-readiness` 已确立的分维度权威原则（详见其 `reference/methodology.md` 的"UI 设计稿基准原则"）：

- **行为逻辑**（交互结果、启用禁用条件、数据来源）：需求文档 > 设计稿/原型图。
- **UI 呈现**（元素存在与否、位置、布局、视觉样式）：有设计稿时设计稿 > 需求文档 > 原型稿。

### 检查维度

1. **行为逻辑核对**：以需求文档为基准，检查设计稿呈现的交互结果、启用/禁用条件是否与需求描述一致；设计稿明显违背需求描述的行为逻辑时判定为问题。
2. **UI 呈现覆盖核对**：以设计稿为基准，检查需求文档/原型图中提到的元素、页面、状态在设计稿中是否有对应呈现。**设计稿缺失某个需求提到的元素时，先排查是否存在"设计稿引用/复用了已有页面或组件"的可能**（例如需求描述的场景本身就是复用一个已有的列表页、弹窗或流程），无法排查清楚时默认判定为"需要澄清"而不是"阻断"——设计稿没有画出某个东西不必然等于遗漏。
3. **关键状态覆盖**：需求文档提到的空状态、异常状态、加载中、权限受限等状态，是否在设计稿中有对应呈现；这类状态最容易被设计稿遗漏，也最容易被误判为"合理复用"，需要单独确认而非一概而论。

### 严重度判定示例

- **阻断级**：设计稿呈现的交互结果与需求文档描述的行为逻辑直接冲突（例如需求要求"提交前需二次确认"，设计稿流程直接跳过确认环节）。
- **需要澄清**：需求提到的元素在设计稿中找不到，且没有明确证据表明是合理复用已有页面（这是本阶段最常见的分级，默认从这里开始，不要不加区分地升级为"阻断"）。
- **轻微/不判定**：视觉细节层面的出入（间距、颜色深浅等）不在本 Skill 判断范围内，多模态模型对这类精度不可靠，不产出相关结论。

## 材料获取与证据降级

- **需求文档**：优先直接读取文件内容或访问链接原文，标注 `[已核对]`；链接不可访问时请求用户提供文本或截图并标注 `[用户提供]`；仍无法获取时该阶段判定 `[未确认]`，报告中说明"因材料缺失，本阶段核对范围受限于 XX"，不假装已核对。
- **原型图**：内嵌在需求文档中的直接读取；有独立链接且可访问时读取原始内容；否则按上一条同样降级处理。
- **设计稿**：蓝湖等工具的链接，若环境中有对应 MCP 工具可用且核对确实需要时可以调用获取数据；数据体量大时**原样落盘为独立文件，报告正文只放引用**（链接、稿件标识、数据文件路径、采集时间），不把 AI 对设计稿内容的自然语言转译当作下游判断依据（复用 `development-readiness` 已确立的"基准不得有损转译"原则，避免转译失真）；没有 MCP 工具或用户未提供设计稿数据时，退回用户提供的图片/描述并标注 `[用户提供]`；完全没有设计稿时该阶段判定为"无法核对"（不是"不可用"——是核对范围内没有材料可比对），如实说明，不推测设计稿内容。

## 报告落点与更新规则

- 路径：`docs/requirement-consistency-check/<需求文档名>-consistency-check.md`。需求文档名取用户提供的文件名或文档标题，去除扩展名，文件系统不安全字符（`/ \ : * ? " < > |` 等）替换为连字符。
- **同名覆盖更新，不保留历史版本**；报告顶部必须记录"核对时间"与"对应需求文档版本/最后修改标记"（文件最后修改时间、文档系统的版本号或最后编辑时间；均无法获取时记录 `[未确认]` 并说明），避免报告被误当作反映最新需求文档状态的结论使用。
- 用户显式收窄核对范围时，报告中注明"本次范围：仅阶段 X"；未覆盖的阶段结论记为"未评估"，不当作"可用"处理。
