# Requirement Consistency Check

## Problem

部分需求文档由 AI 撰写、缺少人工校对，容易出现术语定义前后不一致、逻辑跳跃、举例与规则不符等问题；需求文档被反复修改时，改动也常常没有同步到所有相关段落，导致文档内部自相矛盾。此外，设计稿有时未能完全遵循需求文档和原型图，这类出入往往要到开发或验收阶段才被发现，返工成本更高。

这些问题如果带着进入开发就绪评估甚至直接开发，会让后续所有判断都建立在不可靠的材料上。

## Goal

在进入 [`development-readiness`](../development-readiness/README.md) 之前，按先后顺序核对一份需求资料的可信度：

1. **需求文档自查**：文档内部是否前后一致，是否存在未经校对的矛盾或残留的旧版本内容。
2. **需求文档 vs 原型图**：功能覆盖和交互流程是否对得上。
3. **需求文档 + 原型图 vs 设计稿**：按"行为逻辑 vs UI 呈现"分维度核对是否存在遗漏或明显出入。

三阶段默认严格顺序、阻断式推进——需求文档自身都自相矛盾时，继续比对原型图/设计稿没有意义。产出是分级问题清单和阶段结论，帮助需求方/设计方/开发方就"以哪个为准"达成一致，**目的是收敛一致，不是证明谁对谁错**，因此本 Skill 只发现问题、绝不代替任何一方修改材料本身。设计背景见
[`2026-08-28-requirement-consistency-check-design.md`](../../../docs/superpowers/specs/2026-08-28-requirement-consistency-check-design.md)。

## Use Cases

- 需求文档由 AI 生成或经过多轮修改，希望在开发前先确认其内部逻辑没有自相矛盾。
- 需求文档修改后，担心原型图或设计稿没有跟着同步。
- 接手一个任务前，希望先确认需求资料本身可信，再进入 `development-readiness` 做开发就绪评估。
- 需要一份中性的问题清单，推动产品/设计/开发就材料出入达成一致，而不是相互指责。
- 只想核对某一个阶段（例如已经确认过需求文档没问题，这次只想比对设计稿），可以显式指定范围。

## Not For

- 判断需求该不该做、优先级如何（产品职责）。
- 判断开发是否就绪、环境是否可用（属于 [`development-readiness`](../development-readiness/README.md)）。
- 修改需求文档、原型图或设计稿本身。
- 像素级/逐元素视觉比对（判断"间距差几 px"不在多模态模型可靠范围内）。
- 记录开发后发现的问题（属于 [`task-issue-record`](../task-issue-record/README.md)，那是任务交付物问题，本 Skill 针对的是开发前的需求资料）。

## 形态说明

这套指令需要向用户呈现问题清单、并在阻断时说明"为什么先停在这里"，属于人在环、单会话内也可能跨轮的工作流，因此作为主对话中的 **Skill**。`SKILL.md` 以渐进披露组织：常驻的只是精简内核，详细检查维度按需读入 `reference/methodology.md`。

本 Skill 不需要 Shell、代码执行或 Git 能力，只需要文件读取和链接访问能力。

## Usage

### Claude Code

作为 Agent Skill 使用：将本目录放到 Claude Code 能发现 Skill 的位置，`SKILL.md` 的 frontmatter `description` 用于自动触发；也可配一个 slash command（如 `/requirement-check`）作为显式入口。

### Codex 或其他工具

将 [`SKILL.md`](SKILL.md) 作为主 Agent 指令使用，需要细节时按其中指针读取 `reference/methodology.md`。确保 Agent 具备文件读取能力；如需访问在线文档/设计稿链接或调用设计稿类 MCP 工具，需相应授权。

### Suggested Start

```text
请使用 Requirement Consistency Check 帮我核对这份需求文档：<需求文档路径或链接>

原型图：<内嵌在需求文档中 / 独立链接 / 暂无>
设计稿：<蓝湖链接 / 图片文件路径 / 暂无>
```

只想核对某一阶段：

```text
这份需求文档我已经确认过没问题了，请只帮我核对需求文档+原型图和设计稿之间的 gap：
需求文档：<路径或链接>
原型图：<内嵌 / 链接 / 暂无>
设计稿：<蓝湖链接或图片路径>
```

报告默认写入 `docs/requirement-consistency-check/<需求文档名>-consistency-check.md`，同名覆盖更新，无需额外授权。

## Inputs

必需：

- 需求文档（文件路径或链接）。

可选：

- 原型图（内嵌在需求文档中，或独立文件/链接）。
- 设计稿（蓝湖等工具链接，或图片文件）；没有设计稿时阶段三判定为"无法核对"，不影响阶段一、二独立进行。
- 用户明确指定的核对范围（只做某阶段/跳过某阶段）。

## Expected Behavior

Agent 应：

- 通读需求文档全文并跨章节交叉核对，而不是只做关键词匹配或抽样检查。
- 把每一条发现的问题分级（阻断级/需要澄清/轻微），并给出可追溯到原文位置的证据。
- 发现矛盾时呈现双方原文，使用中性语言，不评判谁对谁错，不擅自选择以哪一方为准。
- 阶段一存在阻断级问题时先停下并说明，不带着自相矛盾的需求继续做阶段二、三。
- 阶段二核对功能覆盖与交互流程，不把原型图的视觉布局当作判断依据。
- 阶段三区分"行为逻辑"与"UI 呈现"两个维度分别核对；设计稿缺失元素时先考虑是否为合理复用已有页面，默认降级为"需要澄清"而非直接"阻断"。
- 材料无法访问或缺失时明确标注证据等级为 `[未确认]`，如实说明核对范围受限，不假装已核对。
- 设计稿数据体量较大时原样落盘引用，不把 AI 的自然语言转译当作下游判断依据。

Agent 不应：

- 修改需求文档、原型图或设计稿本身。
- 判断需求该不该做、优先级如何，或需求文档修改后该以哪个版本为准。
- 做像素级/逐元素的视觉比对，或对无法可靠判断的视觉细节下结论。
- 在材料缺失或无法访问时臆测材料内容并当作已核对的事实。
- 把"设计稿没画出某个元素"一律当作阻断级问题，而不考虑合理复用的可能。

## Evidence Labels

- `[已核对]`：直接读取到需求文档/原型图/设计稿的原文、原图或原始数据后得出的结论。
- `[用户提供]`：材料无法直接访问，由用户转述或提供文本/截图。
- `[未确认]`：材料缺失或无法访问，证据不足。
- `[证据冲突]`：不同材料之间描述不一致，需同时保留双方来源引用。

## Human Confirmation

以下事项必须由用户或需求相关方确认：

- 发现矛盾时最终以哪一方描述为准（本 Skill 不代为决定）。
- 设计稿缺失的元素是否确属遗漏还是合理复用已有页面/组件。
- 是否接受"有条件可用"结论下的具体条件，并进入下一步（继续本 Skill 剩余阶段，或进入 `development-readiness`）。
- 是否需要在设计稿类 MCP 工具中主动获取详情数据（涉及额外成本与转译风险）。

## Outputs

```
docs/requirement-consistency-check/<需求文档名>-consistency-check.md
```

同名覆盖更新，不保留历史版本；报告内记录核对时间与对应需求文档版本/最后修改标记。每个阶段给出「可用 / 有条件可用 / 不可用 / 未评估」结论和分级问题清单。

## Limitations

- 无法判断需求"该不该做"或业务优先级，这类判断留给产品。
- 无法做像素级视觉比对，只能判断"明显不是一回事"级别的出入。
- 判断"设计稿缺失元素是否为合理复用"依赖上下文线索，线索不足时只能标记"需要澄清"交给人工判断，不保证百分之百准确分类。
- 不保留历史版本，无法自动比较"这次改动相对上次核对有什么变化"；如需要历史追溯，需用户自行保存历次报告。
- 材料获取依赖用户提供的访问权限；无法访问的在线文档/设计稿只能降级为 `[用户提供]` 或 `[未确认]`。

## Roadmap

- 待真实使用积累失败案例后，评估是否需要补充独立的评估场景文件（参照 `task-issue-record` 先例，首个版本保持轻量，不预先投入）。
- 评估 `development-readiness` 归集需求文档到 `raw/` 时是否应主动检查是否存在对应的核对报告，目前只做人可读的文档交叉引用。
- 视需要评估是否要为"待确认事项"提供跨会话的状态跟踪机制。
