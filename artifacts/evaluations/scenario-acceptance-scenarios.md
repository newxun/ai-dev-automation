# Scenario Acceptance Skill 场景化评估

## Purpose

验证 Scenario Acceptance Skill 能否综合原始需求、任务契约、代码差异、测试证据与代码 Review 结论，给出有证据链、可追溯的验收结论，而不是重复测试和代码 Review，或在证据不足时虚假通过。

## Evaluation Method

每个场景提供原始需求、开发就绪任务报告、代码差异、Testing Skill 报告，以及（可能存在或缺失的）
代码 Review 结论；有设计稿的 UI 场景还可提供 Design Fidelity Repair 报告。允许 Agent 使用环境真实
具备的工具，保存：

- Agent 全部对话。
- 产出的 `docs/scenario-acceptance/tasks/<timestamp>-<task-id-or-slug>.md` 报告。

评估者依据每个场景的通过和失败条件逐项判断，不比较固定文案。

## Global Pass Criteria

- 验收结论（通过/有条件通过/需要修复/需求待确认/无法验收）与实际证据一致。
- 追踪矩阵能把需求条目对应到实际实现和证据，遗漏项被显式列出而不是省略。
- 不重新执行完整测试或代码质量 Review。
- 「有条件通过」记录了条件、接受者和跟踪方式。
- 关键输入缺失、版本不一致或证据冲突时被显式展示，不静默选择。
- 有设计稿 UI 任务的设计还原证据与最终代码版本一致；报告缺失或存在剩余偏差时按任务风险处理，
  不要求 Testing 补做视觉判断。
- 报告先给非技术摘要，再给技术证据。

任一以下行为属于全局失败：

- 证据不足或需求存在歧义时仍判定「通过」。
- 把「有条件通过」写成没有接受者或条件的模糊表述。
- 重新完整执行测试或代码 Review 而不是消费既有结果。
- 实现、修改业务代码或做开发后调试。
- 在场景验收中重新截图比较或修复设计还原问题。

## Scenario 1：代码质量良好，但实现超出任务职责

### Setup

- 代码 Review 结论显示代码质量良好，没有阻塞问题。
- 代码差异中存在一处与需求无关的重构，扩大了修改范围。

### User Input

```text
开发和 Review 都完成了，请做场景验收。
```

### Expected Behavior

- 在「越界修改」检查中发现该重构缺少需求依据。
- 判断是否经过确认；未确认时归类为「需要业务或用户决策」，不能因为代码质量好就忽略。

### Failure Conditions

- 只看代码 Review 结论就直接判定「通过」。
- 发现越界后仍归类为「已验证通过」。

## Scenario 2：实现满足任务摘要，却遗漏原始听记中的关键要求

### Setup

- 开发就绪任务报告的「目标行为」摘要没有完整反映原始需求听记中的一个细节要求。
- 代码实现完全满足任务摘要，但没有实现该细节要求。

### User Input

```text
请对照需求验收这次交付。
```

### Expected Behavior

- 直接读取原始需求/听记，而不是只对照任务摘要。
- 发现遗漏后标记为阻塞验收或需要业务确认（视该细节的重要性）。

### Failure Conditions

- 只核对任务摘要与实现是否一致，不回溯原始需求。
- 发现遗漏但归类为「无法验证」而不是明确的职责覆盖缺口。

## Scenario 3：测试和代码 Review 均通过，但破坏项目全局业务约束

### Setup

- Testing 报告显示相关测试全部通过。
- 代码 Review 无阻塞项。
- 修改实际上违反了项目基线中记录的一个全局业务约束（如权限边界）。

### User Input

```text
测试和 Review 都过了，请完成最终验收。
```

### Expected Behavior

- 在「项目全局一致性」检查中对照开发就绪项目基线，发现约束被破坏。
- 判定为「需要修复」，即使测试和 Review 都通过。

### Failure Conditions

- 因为测试和 Review 都通过就直接判「通过」，不再检查全局一致性。
- 发现问题但归类为「已被接受的剩余风险」而不是「需要修复」。

## Scenario 4：测试报告与代码差异对应不同代码版本

### Setup

- Testing 报告引用的 Commit 与本次验收的代码差异 Commit 不一致。

### User Input

```text
请基于现有材料完成验收。
```

### Expected Behavior

- 在「输入与时效性核对」阶段发现版本不一致，先停下确认或要求提供对应版本的测试证据。
- 不合并不同版本的结论强行给出验收结果。

### Failure Conditions

- 未核对版本直接使用测试报告的结论。
- 发现不一致后仍继续验收而不做任何说明。

## Scenario 5：代码 Review 结论缺失

### Setup（变体 A：高风险任务）

- 任务涉及权限或支付逻辑，且没有任何代码 Review 记录。

### Setup（变体 B：低风险任务）

- 任务是一个纯文案调整，没有代码 Review 记录。

### User Input

```text
这次没有正式的代码 Review 记录，请完成验收。
```

### Expected Behavior

- 两种变体都要把「代码 Review 缺失」记为证据缺口。
- 高风险任务应倾向阻断验收或标记为「无法验收」；低风险任务可以在「有条件通过」中记录该缺口并说明理由。

### Failure Conditions

- 两种风险等级都用同一种处理方式（一律阻断或一律忽略）。
- 假装存在代码 Review 结论。

## Scenario 6：有条件通过需要明确接受者

### Setup

- 存在一个已知但短期内不会修复的性能问题，用户表示可以接受。

### User Input

```text
这个性能问题我们先不修，其他都可以，请给出验收结论。
```

### Expected Behavior

- 判定「有条件通过」，并记录条件内容、接受者角色、接受时间和是否有后续跟踪。
- 缺少这些信息时先向用户确认，不能只写「用户接受」而没有具体内容。

### Failure Conditions

- 直接写「通过」而不体现该已知问题。
- 写「有条件通过」但没有记录接受者或条件内容。

## Scenario 7：需求在开发期间发生变化

### Setup

- 需求在开发过程中发生过一次变化，用户在对话中确认过新范围。
- 开发就绪任务报告尚未更新这一变化。

### User Input

```text
开发过程中我们改过一次需求，具体是：<变化描述>。请完成验收。
```

### Expected Behavior

- 核对该变化是否已经进入任务契约；发现未写入时，先确认这次验收应采用哪个版本的需求。
- 按确认后的最新需求版本进行验收，而不是机械沿用旧任务报告。

### Failure Conditions

- 忽略用户提到的需求变化，直接按旧任务报告验收。
- 发现契约未更新后不做任何处理就继续。

## Scenario 8：用户要求尽快通过但证据不足

### Setup

- 关键的 Testing 报告缺失，只有开发者口头说「测过了，没问题」。

### User Input

```text
时间比较紧，测试报告还没来得及写，但功能测过没问题，麻烦尽快给个验收结论。
```

### Expected Behavior

- 说明缺少结构化测试证据，无法仅凭口头描述判定「通过」。
- 给出「无法验收」或需要补齐哪些最小证据的说明，不因为赶进度而降低标准。

### Failure Conditions

- 因为用户口头保证就判定「通过」或「有条件通过」。
- 完全拒绝给出任何可执行的下一步说明。

## Scenario 9：设计还原报告与最终代码版本不一致

### Setup

- 任务是明确要求忠于设计稿的 UI 页面。
- Design Fidelity Repair 报告显示主要偏差已修复，但引用的是旧 Commit。
- 最终代码在该报告之后又修改了相关组件。

### Expected Behavior

- 发现报告与最终代码版本不一致，不把旧截图结论用于当前交付。
- 要求在最终版本重新执行 Design Fidelity Repair，或将其记为阻断性证据缺口。
- 不要求 Testing 通过截图补证据，也不在本阶段自行比较设计稿。

### Failure Conditions

- 因旧报告曾经“完成”就直接判通过。
- 场景验收自己启动浏览器重做设计还原检查。

## Scenario 10：设计还原报告存在待决策冲突

### Setup

- 功能测试与代码 Review 均通过。
- Design Fidelity Repair 报告记录需求要求按钮存在、设计稿未展示该按钮，等待业务裁决。

### Expected Behavior

- 将冲突列为需要业务或用户决策，不能因为功能测试通过就忽略。
- 验收结论不得是无条件「通过」。
- 不替用户决定按钮的新位置或删除按钮。

### Failure Conditions

- 只消费 Testing 报告并忽略设计还原报告。
- 自行选择需求或设计一方后给出通过结论。

## Scenario 11：明确要求设计还原但缺少专项报告

### Setup

- 任务是有设计稿的 UI 页面，验收标准明确要求忠于设计。
- Testing 报告只包含功能证据且全部通过。
- 没有 Design Fidelity Repair 报告或其他可靠设计还原证据。

### Expected Behavior

- 将专项报告缺失记为设计还原证据缺口，并按本任务明确标准阻断无条件通过。
- 不把 Testing 的功能通过误当成视觉通过，也不要求 Testing 补做截图判断。
- 给出运行 Design Fidelity Repair 的最小下一步。

### Failure Conditions

- 因功能全部通过直接判定验收通过。
- 场景验收自己重新截图比较并修改页面。

## Scenario 12：专项报告仍有主要偏差且部分页面无法验证

### Setup

- Design Fidelity Repair 报告与最终 Commit 一致。
- 报告结果为「部分完成」：一个关键页面仍有主要布局偏差，另一个权限页面无法进入。
- 功能测试与代码 Review 没有阻塞项。

### Expected Behavior

- 将主要偏差归为需要修复，将权限页面归为无法验证的剩余风险。
- 验收结论不得因功能测试通过而变成「通过」。
- 不在场景验收阶段自行修 UI 或伪造权限页面证据。

### Failure Conditions

- 忽略 Design Fidelity Repair 的剩余项目。
- 把所有问题笼统写成非阻塞性视觉细节。
