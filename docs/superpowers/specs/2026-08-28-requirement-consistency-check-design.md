# Requirement Consistency Check 设计文档

## 文档状态

本文沉淀 2026-08-28 与用户的 brainstorming 讨论结论，供 `artifacts/skills/requirement-consistency-check/` 的实现使用。讨论以问答形式逐项收敛，本文按最终决策整理，不逐句还原对话过程。

## 一、问题来源

用户在真实研发中遇到两类需求资料质量问题：

1. **需求文档自身前后矛盾**：部分需求文档由 AI 撰写，缺少人工校对；或者文档被修改过，但改动没有同步到所有相关段落，导致文档内部出现互相矛盾的描述。
2. **设计稿未完全遵循需求文档和原型图**：设计师产出的设计稿与需求文档、原型图之间存在遗漏或出入，且这类问题往往在开发或验收阶段才被发现，成本更高。

用户明确要求核对顺序有先后：**先自查需求文档本身 → 再核对需求文档与原型图的 gap → 再核对需求文档+原型图与设计稿的 gap**，理由是拿一份自相矛盾的需求去比对后续材料没有意义。

## 二、关键决策（逐项来自问答确认）

1. **独立专项 Skill**，不并入 `development-readiness`。原因：`development-readiness` 已经明确拒绝在就绪阶段做"全量 UI 分析或逐元素比对"（见 [`2026-08-28-task-issue-ledger-and-ui-baseline-design.md`](2026-08-28-task-issue-ledger-and-ui-baseline-design.md) 2.3 节），而本次需求恰恰是要做这件事——两者的成本模型和职责边界不同，不能合并。
2. **定位**：`development-readiness` 之前的独立前置步骤。判断"需求资料本身是否可信、三份材料是否对得上"，不判断需求该不该做（产品职责），也不判断开发是否就绪（`development-readiness` 职责）。只有核对通过（或有条件通过并已确认）的需求文档，才有资格作为权威材料进入后续 `development-readiness` 任务的 `raw/` 材料区。
3. **三阶段关系**：默认**严格顺序 + 阻断式**推进——阶段一发现阻断级问题时先停在阶段一，不带着自相矛盾的需求继续做后续比对；但用户可以显式收窄范围（只做某阶段、或跳过某阶段），此时按用户指定范围执行，未覆盖的阶段状态记为"未评估"，不当作"可用"处理。
4. **每阶段产出**：分级问题清单（阻断级 / 需要澄清 / 轻微）+ 阶段结论（可用 / 有条件可用 / 不可用 / 未评估），结论语言风格与 `development-readiness` 的三态就绪结论保持一致，便于未来衔接。
5. **产出边界**：只发现问题、罗列出入，**绝不修改需求文档、原型图或设计稿本身**。发现矛盾时引用双方原文，让需求方自行决定采用哪个版本。这类矛盾通常涉及业务判断，AI 没有资格替产品做取舍；改文档这件事应该由需求方留痕负责。基调是**帮助收敛一致，不是证明谁对谁错**（用户原话："我的目的不是为了 battle，是为了最后需求一致"），报告呈现问题时用中性语言（"两者是否一致需要确认"），不评判对错。
6. **输入材料的获取方式**：不做过度形式区分——需求文档可能是文件或链接，原型图可能内嵌在需求文档中或是独立链接，设计稿一般是蓝湖链接或图片文件。采用"证据降级"思路：能拿到原始数据就用，拿不到就退回用户提供的描述并标注证据等级；"需求文档中直接嵌入设计稿"等边缘情况本次不特殊处理（YAGNI）。
7. **阶段二/三的核对范围复用 `development-readiness` 已确立的分维度权威原则**：
   - 行为逻辑（交互结果、启用禁用条件、数据来源）：需求文档 > 设计稿/原型图。
   - UI 呈现（元素存在与否、位置、布局、视觉样式）：有设计稿时设计稿 > 需求文档 > 原型稿；原型稿默认只用于理解交互流程，不作为视觉布局依据。
   - 因此阶段二（需求文档 vs 原型图）聚焦**功能覆盖与交互流程**，不比较原型图的视觉布局；阶段三（需求文档+原型图 vs 设计稿）按"行为逻辑 vs UI 呈现"分别核对。
8. **阶段一（需求文档自查）是最重要的阶段，需要"综合审查"**：不是关键词扫描或几条规则打勾，而是通读全文、跨章节交叉核对，识别需要推理才能发现的矛盾（术语/字段定义一致性、逻辑完备性与互斥性、版本残留痕迹、举例与规则一致性、AI 生成痕迹如占位符、内部引用一致性）。
9. **阶段三对"设计稿没画"更宽容**：设计稿缺少某个需求提到的元素，可能是合理复用了已有页面/组件，不一定是遗漏。这类出入默认判定为"需要澄清"而非"阻断"，除非有明确证据表明确系遗漏。
10. **命名**：`requirement-consistency-check`（需求一致性核对）。备选 `requirement-readiness` 被否决，理由是"就绪"容易让人误解为判断需求该不该做、优先级是否合理，而这不是本 Skill 的职责。
11. **报告落点**：独立目录 `docs/requirement-consistency-check/`，不挂在 `development-readiness` 下面。**不使用 `tasks/` 子目录和 task-id/slug 机制**——文件名直接跟需求文档本身命名：`docs/requirement-consistency-check/<需求文档名>-consistency-check.md`。原因：这套材料链其他三个 Skill（`development-readiness` / `testing` / `scenario-acceptance`）都是绑定"开发任务"的 slug，而本 Skill 的核对对象是"需求文档"本身，一份需求文档可能对应零个或多个开发任务，也可能在任务被定义前就已经核对过，用任务 slug 命名不自然。
12. **不保留历史版本**：同名覆盖更新，不追加时间戳版本。理由（用户原话）："我的目的不是为了 battle，是为了最后需求一致"——核对的价值在于反映"这份需求文档当前的状态"，不需要历史对比包袱，符合仓库"Stay Small Until Usage Proves Shape"原则。报告内记录"核对时间"和"对应需求文档版本/最后修改标记"，避免过期报告被误当最新结论使用。

## 三、与已有 Skill 的关系

- **不修改 `development-readiness` 的硬边界或方法论**：`development-readiness` 现有的"UI 设计稿基准原则"仍然只服务于"任务能否推进"这一判断，保持不变。本次只在 `development-readiness/README.md` 补充一条文档级的交叉引用，说明存在这样一个前置 Skill，不改变其行为规则。
- **不复用 `task-issue-record` / `task-issue-triage` 的账本机制**：账本记录的是"开发后发现的任务交付物问题"，而本 Skill 核对的是"开发前的需求资料本身"，触发时机、素材来源和裁决主体都不同，不适合合并或复用同一份账本。
- **证据标签自定义，不照搬 `development-readiness` 的五级标签**：`development-readiness` 的 `[代码证据]` `[已验证]`（含运行结果）等标签依赖代码和环境，本 Skill 不涉及代码执行，采用更贴合"文档核对"场景的标签集合：`[已核对]` `[用户提供]` `[未确认]` `[证据冲突]`。

## 四、明确不做的事

1. **不做像素级/逐元素视觉比对**：复用仓库已有共识（多模态模型只能可靠判断"明显不是一回事"级别的出入，无法可靠判断"间距差 3px"），详见 [`2026-08-28-task-issue-ledger-and-ui-baseline-design.md`](2026-08-28-task-issue-ledger-and-ui-baseline-design.md) 4.3 节。
2. **不建立需求文档版本历史/diff 机制**：不保留历史核对版本，也不自动比较"这次改动相对上次修改了什么"；如未来证明有必要，属于独立的后续迭代。
3. **不引入独立的评估场景文件**（`artifacts/evaluations/requirement-consistency-check-scenarios.md`）：参照仓库最新一批 Skill（`task-issue-record` / `task-issue-triage`）的先例——两者同样是新增的专项 Skill，均未配套独立评估场景文件，保持轻量，待真实使用积累失败案例后再补充，不在首个版本预先投入。
4. **不修改 `development-readiness` 现有的原始资料归集规则**，只在文档中做一次性交叉引用说明前置关系。

## 五、后续开放问题（本次不实现，留待真实使用后决定）

1. `development-readiness` 是否应该在归集需求文档到 `raw/` 时，主动检查是否存在对应的 `requirement-consistency-check` 报告——本次不实现自动联动，仅在两侧文档里做人可读的交叉引用。
2. 是否需要给"待确认事项"提供更结构化的跟踪机制（比如状态可变、可勾选）——本次只做一次性报告罗列，不引入状态机，若后续证明同一批问题需要跨会话反复跟踪，再参考 `task-issue-record` 的账本模式演进。
