# 任务问题账本与 UI 设计稿基准原则 设计文档

## 文档状态

本文沉淀 2026-08-28 的方案讨论，供后续实现使用。讨论从「AI 做 UI 验收」出发，
经过可行性评估后大幅收敛，最终确定两项改动：一项是给 `development-readiness`
补一条轻量原则，一项是新增一对问题记录 Skill。

本文同时记录了**被否决的重型方案及其理由**，避免后续重复提出。

## 一、问题来源

### 1.1 触发本次讨论的真实失败

用户在一个有蓝湖设计稿的前端任务中连续遇到三类问题：

1. **设计稿基准被有损转译**：就绪阶段提供了蓝湖链接，MCP 取回数据后被 AI 解析成
   自然语言写进就绪文档。开发阶段读到的是这份「文字二手稿」，UI 大幅偏移，完全不可用。
2. **就绪文档未记录设计稿链接**：原始来源丢失，后续阶段无法回到原稿核对。
3. **重新用 MCP 开发后仍有明显出入**，典型表现是「做出来的不是同一个东西」而非像素级偏差：
   - 需求文档写了「还原」功能、设计稿上没有对应按钮，AI 直接按需求文档实现并添加了该按钮，
     全程未提示这处冲突。
   - 集团切换选择器在设计稿的 header 左侧，实现放到了 header 右侧，而设计稿右侧本是其他内容。
     疑似受原型稿误导或模型幻觉。

### 1.2 真正的共性

第 3 类的两个例子有同一个根因：**AI 在多个互相冲突的信息源之间自行做了选择，且没有暴露这个选择。**
这不是比对精度问题，是信息源权威性未定义、冲突未被展示的问题。

### 1.3 讨论中浮现的更根本痛点

讨论后期用户指出，比 UI 验收更缺的是**问题的落点**：

- 开发阶段常使用其他工作流，那些工作流「开发完就结束了」。
- 开发后自行走查发现的问题（不限 UI，也包括业务、逻辑、代码质量、技术规范）无处安放。
- 以往用临时 review 文档记录，事后找不到。
- 希望不只服务当前任务，还能支持后续复盘。

这个需求不挑问题类型、不依赖特定工作流被调用，复用价值高于任何单点的 UI 比对能力，
因此成为本次的主要产出。

## 二、决策一：`development-readiness` 补充 UI 设计稿基准原则

### 2.1 现有缺口

交接文档 `2026-08-20-readiness-testing-acceptance-handoff.md` 第 4.2 节给出了判断目标行为时的
权威来源顺序：用户最新确认 → 本次采用的原始需求 → 历史需求或会议记录 → 当前代码行为。

**这份清单里没有设计稿。** 因此 1.1 中「按需求文档加了个设计稿上没有的按钮」的行为，
按现有规则其实是合规的——需求文档是最高权威，设计稿不在名单上。

### 2.2 要补充的内容

分维度定义权威来源，不一刀切：

- **UI 呈现**（元素存在与否、位置方位、布局结构、视觉样式）：设计稿 > 需求文档 > 原型稿。
- **行为逻辑**（交互结果、启用禁用条件、数据来源）：需求文档 > 设计稿。

单独写死一条：**原型稿（Axure / PRD 内的示意图）只用于理解交互流程，不作为视觉布局依据。**
原型上的元素位置通常是随手摆放的，把它当布局依据是 1.1 中第二个例子的可能成因。

以及：**发现设计稿与需求文档/原型稿存在出入时必须明确提出，不得静默选择其一后继续实现。**

有设计稿的 UI 任务，就绪文档必须记录设计稿链接或稿件标识。

### 2.3 适用范围与成本约束（关键）

本条原则**只适用于有设计稿的 UI 任务**。没有设计稿的 UI 任务、以及全部非 UI 任务直接忽略，
不因此增加任何分析动作。

**不得在就绪阶段做全量 UI 分析或逐元素比对。** 用户明确拒绝为此消耗 Token：就绪阶段只负责
判断任务能否推进。这里要的是一条**原则加一次冲突暴露**，即遇到明显出入时提出来，
而不是主动发起一轮设计稿核对。

### 2.4 关于「基准不得有损转译」

1.1 中第 1 类失败的成因是：设计稿类 MCP 的返回天然巨大（多个蓝湖 MCP 的文档都写明
`analyze` 返回过大需用 `include` 裁剪、`full` 过大自动降级 `summary`、`summary` 仍过大则截断），
AI 在上下文压力下把它总结成自然语言，是可预期的行为而非偶然。

对应约束是：MCP 取回的数据原样落盘为独立文件，就绪文档正文只放引用（链接、稿件标识、
数据文件路径、采集时间），不放设计稿内容的自然语言描述作为下游信息源。

本条与 2.3 的成本约束不冲突：落盘是存储动作，不是分析动作。但用户在讨论收尾时只明确要求了
2.2 的原则部分，未再提及落盘，因此**本条是否纳入本次实现范围需先与用户确认**（见 5.5）。
若纳入，须保持最小形态，不引入分片、索引、版本指纹等机制。

## 三、决策二：新增任务问题账本 Skill（一对）

### 3.1 目标

为「开发后发现的各类问题」提供一个稳定、可追加、可复盘的落点，覆盖 UI、业务、逻辑、
代码质量、技术规范等任意类型，且不依赖特定开发工作流。

### 3.2 拆成两个 Skill

参照仓库已有的 `skill-bug-record` / `skill-bug-triage` 模式，拆分为记录与处理两个 Skill：

- **记录 Skill**：只把问题追加进账本。硬边界是不判断、不修任何文件、不评估严重性是否成立。
- **处理 Skill**：读取未处理条目，判断并实施修复，即时回写状态。

**拆分理由**：记录侧的边界必须绝对干净。若同一个 Skill 既能记录又能修复，
AI 在记录过程中会倾向于「顺手修掉」，导致账本残缺——而账本残缺正是「事后无法复盘」的根因。
两者的调用时机（会话末尾 / 决定处理时）、能力要求和风险模型也完全不同。合并会导致
description 含义模糊，硬边界自相矛盾（一条禁止修改代码，一条要求实施修复）。

### 3.3 账本落点（关键约束）

用户要求账本与任务就绪文档同处一个便于按任务查找的位置。

**文件名必须只跟任务走，不跟会话走。** 现有 Skill 的落点形如
`docs/<阶段>/tasks/<会话时间戳>-<slug>.md`，会话时间戳在文件名中。账本若沿用此模式，
每次会话都会新建文件，同一任务的问题散落在多个文件中，将直接复现「事后找不到」的问题。

账本是**跨会话、跨阶段、长期追加、状态可变**的文档，这与现有「一次会话一份报告」的模式
不同，实现时需要为它选择合适的命名与落点，而不是机械套用现有约定。

### 3.4 条目要求

- 使用 Markdown checkbox 表达是否已处理。
- checkbox 之外需要状态字段区分已修复 / 不修复 / 延后等结果，仅有勾选无法表达「决定不修」。
- 分类至少覆盖 UI、业务、逻辑、代码质量、技术规范，且必须可扩展，不设为封闭枚举。
- 字段设计需服务于复盘目标（例如事后能看出哪类问题反复出现），因此需记录发现时间、
  来源阶段或场景、分类、现象、涉及位置、状态。
- 追加式写入，不重写历史条目；状态变更就地更新，不删除条目。

### 3.5 记录来源

两种触发方式：

1. 用户主动提出某个问题。
2. 一次开发会话结束后触发，从本次会话中归集问题。

第 2 种存在风险：AI 可能把会话中已经修复的问题也记进账本，或臆造问题。因此需要边界约束——
只记录确实未解决、且经用户确认的问题。分类属于描述而非裁决，记录 Skill 可以做分类，
但不得判断问题是否成立、是否需要修复。

### 3.6 处理侧要求

- 支持只处理部分条目，其余保持未处理状态。
- 每处理完一条立即回写状态，不批量延后更新。
- 涉及影响面较大的修改时先说明方案再实施。

## 四、明确不做的事

以下方案在讨论中被提出并否决，记录理由以避免重复提出。

### 4.1 不做设计稿节点与 DOM 的自动映射比对

一度设计过：Design IR 节点与 DOM 元素自动映射 → 属性级数值 diff → 节点指纹 →
偏离登记表与豁免自动失效。该方案被否决。

**否决理由**：调研发现这正是开源项目 `design-drift` 已实现的东西——它用文本锚点、
全局仿射估计、几何/结构/样式加权打分完成映射，写入 `.mappings.lock.json`，
歧义项标记 `needsReview`，由 `config-schema` / `figma-client` / `capture` / `pixel-diff` /
`element-diff` / `auto-match` / `cli` / `viewer` 八个包构成。

**这是一个工程系统，不是一份 Skill 文档能承载的东西。** Skill 的定位是沉淀使用规范
（参照 `yunxiao-devops-workflows`：不新增能力，只规定取证顺序与安全模型），
把工程复杂度塞进文档会让工作流难用且无法维护。

此外 Uiprobe 的行业分析指出，属性级比对工具的效果「完全取决于元素映射的质量」，
这恰恰是最脆弱、也最难靠提示词保证的一环。

### 4.2 不自研设计稿比对工具

市面上该品类已成熟：Fidel（PR 上校验，0–100 还原度评分，逐元素比对 28 个 CSS 属性）、
design-drift（开源，像素 + 元素双层 diff，含 token drift 检测）、Loupe、Uiprobe、
Applitools Eyes 的 Figma 插件（企业定价）、以及 PerfectPixel / Over.fig 等叠图插件。

但这些工具**全部绑定 Figma REST API，均不支持蓝湖**。

若未来确有需求，性价比最高的路径是给 `design-drift` 这类开源工具增加蓝湖数据源
（其 `figma-client` 是独立包，而蓝湖 MCP 本身读取的就是蓝湖缓存的 Figma 原始导出，
数据形态同源），而不是自己写一套 Skill 去模拟工程能力。

### 4.3 不做像素级 UI 判定

多模态模型的可靠边界很明确：判断「设计稿有这个元素、实现里没有」「这块整体错位了」
是可靠的；判断「间距差 3px」「这个灰深一档」是不可靠的，典型输出是
「整体基本一致，细节略有差异」，无使用价值。

用户的实际痛点全部落在可靠区间内（「明显就不是一个东西」），因此不需要像素级能力。

### 4.4 不在就绪阶段做 UI 冲突的主动全量分析

见 2.3。用户明确拒绝为此消耗 Token。

### 4.5 不做偏离登记表与豁免失效机制

用户提出过真实场景：部分 UI 改动设计师不会同步更新设计稿，这些已被接受的偏离不应被
反复报出。原设计为此引入节点指纹与豁免自动失效，已随 4.1 一并否决。

后续若确有需要，最简形态是把上一轮走查结论作为下一轮输入，已确认接受的条目降级显示，
不引入指纹、状态机等机制。

### 4.6 视觉回归与设计还原度是两件事（供后续参考）

- **视觉回归**：改动前 vs 改动后，目的是防止连带破坏，属于 `testing` 职责。
- **设计还原度**：设计稿 vs 实现，基准来自外部设计稿。

这是行业共识而非本次自创：Percy、Chromatic 等回归工具只比较构建之间的差异，
若开发一开始就把间距做错，它们会把错误实现当作基线批准，永远不会报出。

现有 `artifacts/skills/testing/reference/visual-testing.md` 把两者混写在一起，
其中「对比设计稿与实现」的表述缺少基准来源机制。本次不改动该文件，
但后续若重新触及视觉测试，应注意这一区分。

## 五、待确认与后续

实现阶段需要确定，本次讨论未定的内容：

1. 账本文件的具体落点与命名（须满足 3.3 的约束）。
2. 两个新 Skill 的具体命名（须与现有 `skill-bug-record` / `skill-bug-triage` 区分开，
   后者针对的是 Skill 自身定义的问题，本次针对的是任务交付物的问题）。
3. 条目状态取值集合的最小形态。
4. 账本与 `scenario-acceptance` 的关系：验收阶段是否消费账本中的未处理条目。
   本次不实现，但命名与格式设计时应为其留出可能。
5. 2.4 的「MCP 数据原样落盘、禁止转译」是否纳入本次实现范围。用户此前明确表达过
   「不能有损固化」，但收尾时只要求了 2.2 的原则，需要确认。

本次不改动 `testing`、`scenario-acceptance` 及 `visual-testing.md`。
