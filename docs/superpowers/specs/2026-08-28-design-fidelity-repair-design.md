# 设计还原度诊断与修复 Skill 设计文档

## 文档状态

本文记录 2026-08-28 已确认的设计方案，供后续编写实现计划使用。

这项能力不命名为「UI 验收」。它不是交付阶段的最终裁决，而是一个针对 UI 呈现的
**设计还原度诊断—修复循环**：读取权威设计源、在浏览器中采集真实实现、从多个角度发现偏差、
修改代码并重新验证。最终 UI 验收仍由人完成。

## 一、问题与目标

### 1.1 问题

使用蓝湖 MCP 或设计稿图片辅助开发时，初次实现可能已经有较高还原度，但仍会留下元素缺失、
方位错误、布局层级不一致或整体视觉观感明显偏离等问题。开发会话通常还承载需求理解、编码、
调试等上下文，模型不一定能持续专注于设计还原。

开发后在一个上下文干净、目标单一的流程中重新读取设计源并直接比较画面，能够发现另一批问题。
这不是无意义地重复开发阶段的蓝湖调用，而是以不同任务目标进行独立复查。

### 1.2 目标

新增独立的 `design-fidelity-repair` Skill：

1. 支持用户显式指定设计来源，也能从当前任务材料中自动发现来源。
2. 首版支持两类真实高频来源：蓝湖链接与设计稿图片。
3. 浏览器截图对比始终执行；有蓝湖来源时额外执行蓝湖 MCP 结构化核对。
4. 发现设计还原偏差后允许修改代码，并通过重新截图形成有限修复循环。
5. 将诊断与修复职责分离，让视觉诊断运行在干净、单一目标的上下文中。
6. 留存可追溯证据，但不替代人的最终 UI 验收。

### 1.3 成功标准

- 能发现「明显不是同一个东西」级别的问题，包括元素缺失、多余元素、主要区域错位、布局结构错误、
  视觉层级异常和明显样式偏差。
- 蓝湖任务同时使用结构化设计信息与画面直接对比，不只消费开发阶段的自然语言总结。
- 修复后的最终结论来自新一轮浏览器截图和独立视觉复查，而不是只检查代码。
- 视觉修复不会静默改变需求行为；设计与需求冲突会暴露给用户。
- 无法取得设计基准、无法启动页面或无法进入目标状态时，不宣称还原修复完成。

## 二、定位与边界

### 2.1 与现有 Skill 的关系

- `development-readiness`：记录任务范围、设计稿链接或图片材料，是自动发现设计来源的首要入口。
- `testing`：产出测试证据且禁止修改业务代码；它的视觉回归关注「修改前 vs 修改后」。
- `scenario-acceptance`：综合需求与证据给出最终交付结论，禁止实施修复。
- `design-fidelity-repair`：关注「设计稿 vs 实现」，允许诊断后修改代码，因此必须独立存在。

`scenario-acceptance` 可以消费本 Skill 的报告，但本 Skill 的完成不等于场景验收通过。

### 2.2 明确不做

- 不做人的最终 UI 验收或业务验收。
- 不承诺像素级精确判断，不把 3px 间距或细微色差作为模型可稳定裁决的目标。
- 不验证完整业务逻辑；只运行防止视觉修复破坏功能所需的相关测试。
- 不首版支持 Figma、Sketch 等当前很少使用的来源，也不提前建立通用插件框架。
- 不在 Skill 中指定、推荐或写死模型。用户在启动会话时自行选择具备所需能力的模型。
- 不进行无边界的全站、全状态和全断点遍历。

## 三、总体架构

Skill 是人在环的主工作流，负责输入核对、来源路由、比较范围、浏览器取证、修复控制和报告。
视觉诊断由独立 Agent 执行，以保持上下文干净；主 Agent 负责解释诊断结果、修改代码和运行必要测试。

```text
用户指令 / 当前消息 / 开发就绪任务材料
                  ↓
            设计来源解析
          ┌───────┴────────┐
          ↓                ↓
    蓝湖 MCP 结构核对    设计画面基准
          └───────┬────────┘
                  ↓
       浏览器采集真实实现关键状态
                  ↓
      独立视觉 Agent 直接比较画面
                  ↓
       偏差合并、冲突检查与分级
                  ↓
        主 Agent 修改代码并测试
                  ↓
       浏览器重新截图、独立复查
                  ↓
        最终证据与剩余问题报告
```

蓝湖 MCP 与截图对比是互补关系：

- MCP 适合核对元素、层级、尺寸、样式等结构化设计信息。
- 画面比较适合发现整体构图、相对方位和视觉层级等感知偏差。
- 只有设计稿图片时，仍可从图片提取显式观察清单并做画面对比，但不能声称拥有蓝湖结构化证据。

## 四、输入发现与路由

### 4.1 查找优先级

1. **用户显式指定**：当前指令指定的蓝湖链接或设计稿图片优先。
2. **当前消息自动识别**：用户未指定方式，但消息中包含蓝湖链接或图片时自动路由。
3. **任务材料自动发现**：当前消息没有来源时，根据任务 slug 定位最新的
   `development-readiness` 任务文档，再读取其中引用的设计链接、稿件标识和 `raw/` 材料。
4. **最小确认**：仍找不到来源、存在多个无法判定的候选、来源失效或来源互相冲突时，向用户提出
   一个会改变执行结果的最小问题。

不得用当前实现反推设计基准，也不得为了寻找设计稿对整个仓库或外部系统做无边界探索。

### 4.2 路由规则

- 蓝湖链接：调用可用的蓝湖 MCP，获取结构化信息和原始设计画面。
- 图片或附件：直接作为设计画面基准。
- 同时存在蓝湖链接和图片：蓝湖提供结构化信息；图片作为视觉基准。若两者不一致，先展示冲突。
- 用户显式指定来源时，不被自动发现的其他候选静默覆盖。

用户指定的是**设计来源**，不是默认关闭视觉对比。完整流程的浏览器画面对比始终执行；只有用户
明确要求缩小流程时才可跳过，并必须把结果标记为不完整验证。

### 4.3 后续扩展

首版不实现 Figma。未来出现真实 Figma 任务时，在保持同一输出协议的前提下新增第三条来源路由，
无需提前设计抽象插件系统。

## 五、比较范围与浏览器取证

### 5.1 关键状态矩阵

从任务范围和开发就绪材料中选择最小充分状态，例如：

- 页面默认加载完成状态。
- 本次修改直接涉及的弹窗、抽屉、菜单或选中状态。
- 需求明确涉及的空数据、权限或错误状态。
- 受影响的桌面端与移动端关键断点。

不因为页面存在更多状态就全部遍历。每个状态都要记录对应设计画面、实现路由、准备步骤和视口。

### 5.2 浏览器截图是必经步骤

实现画面必须来自启动后的真实应用：

1. 启动或复用项目服务。
2. 浏览器进入目标路由并准备确定性测试数据。
3. 设置固定视口、DPR、主题、语言、字体和动画策略。
4. 等待页面达到约定稳定状态。
5. 截取关键状态，保存与状态矩阵对应的证据。

初始诊断和最终复查必须进行完整关键状态截图。中间修复轮次可只复查发生变化的页面或区域，
以控制成本。

### 5.3 设计画面获取

- 蓝湖：优先使用 MCP 返回或导出的原始设计画面，避免浏览器缩放、工具栏和标注层污染。
- 蓝湖 MCP 无法提供可比较画面时：可在具备访问条件的浏览器中打开蓝湖并采集，但要固定缩放、
  隐藏无关界面并记录这是降级来源。
- 图片：保留原图；必要时只做去除浏览器外框、批注或无关留白等非有损裁切，不重新生成设计内容。

## 六、诊断与偏差处理

### 6.1 独立视觉诊断契约

视觉 Agent 每次只获得：

- 本轮需要比较的设计画面与实现截图。
- 状态名称、视口以及必要的设计源结构化事实。
- 明确的判断边界和输出格式。

不把开发会话的长上下文、此前的自我辩护或预设结论整体交给视觉 Agent。输出至少包含：

- 页面、状态和区域。
- 设计预期与实现现状。
- 偏差类别：缺失、多余、位置、布局、层级、尺寸、样式或无法判断。
- 严重程度：阻碍使用/主要偏差/次要偏差。
- 证据引用和判断置信度。

低置信度、细微像素差异和来源本身不清晰的项目不能自动升级为确定缺陷。

### 6.2 信息源权威性

- UI 呈现（元素存在、位置方位、布局结构、视觉样式）：设计稿优先于需求文档和原型稿。
- 行为逻辑（交互结果、启用条件、数据来源）：需求文档优先于设计稿。
- 原型稿只用于理解流程，不作为视觉布局依据。

设计稿与需求的行为要求冲突，或设计稿之间互相冲突时，不得静默选择并继续修复；记录证据后请用户
裁决。

### 6.3 已接受偏差

报告中维护本任务已由用户确认接受的偏差。后续轮次仍显示它们，但标记为「已接受」，不重复自动
修复。首版不引入节点指纹、复杂豁免状态机或自动失效机制；当设计来源明显更新时，提示重新确认
已有例外是否仍适用。

## 七、自动修复循环

### 7.1 修改边界

默认可直接修复：

- CSS、设计 token、颜色、字体、间距、尺寸和对齐。
- 不改变业务含义的布局与表现层结构。
- 明确缺失或多余、且设计与需求不存在冲突的装饰性 UI 元素。

必须先确认：

- 新增、删除或改变有业务行为的按钮、入口和交互。
- 改变组件公共 API、大范围重构共享组件。
- 修复可能影响其他页面，且没有足够回归证据。
- 设计源与需求、当前产品行为或另一份设计源冲突。

### 7.2 循环步骤

1. 合并蓝湖结构核对与视觉 Agent 的发现，去重并排除已接受偏差。
2. 按主要结构问题优先、局部样式问题后置的顺序修复。
3. 运行与修改范围匹配的最小功能测试。
4. 浏览器重新加载并截图。
5. 使用新的独立视觉诊断上下文复查。

默认最多执行三轮自动修复。提前达到主要偏差消失时立即结束；三轮后仍反复出现、不同证据无法
一致、只能依赖主观像素判断或继续修改会越界时停止，将剩余问题交给用户。

### 7.3 完成条件

同时满足以下条件才可声明本流程完成：

- 所有关键状态均有最终浏览器截图。
- 主要设计还原偏差已修复，或被明确记录为用户接受/待决策。
- 最后一轮由新的视觉诊断上下文完成。
- 相关最小功能测试没有显示视觉修复造成回归。
- 设计来源、代码版本和证据能够互相对应。

## 八、报告与证据

每次运行创建：

`docs/design-fidelity-repair/tasks/<timestamp>-<task-id-or-slug>.md`

报告至少记录：

- 任务、代码 Commit 与工作树状态。
- 设计来源、稿件标识或文件路径、采集时间和来源优先级。
- 浏览器环境与关键状态矩阵。
- 初始偏差清单及蓝湖/视觉证据来源。
- 每轮修改摘要、测试结果和复查结果。
- 修复前后截图位置。
- 已修复、已接受、待用户决策和无法验证的剩余项目。
- 最终声明：完成、部分完成或无法完成；不得使用「最终 UI 验收通过」。

报告可供 `scenario-acceptance` 消费。是否将问题同步到任务问题账本，由用户或后续工作流决定，
本 Skill 不自动制造重复记录。

## 九、异常与降级

- 蓝湖 MCP 不可用：若已有可靠设计图片，可继续视觉路径并标记结构化核对缺失；否则停止。
- 设计链接失效或无权限：尝试任务材料中的安全快照；仍不可用则请求用户提供，不绕过权限。
- 项目无法启动：记录启动证据和阻断，不以静态代码检查替代浏览器验证。
- 页面依赖不可获得的数据或权限：使用已授权的测试数据；不得写生产数据或擅自扩大权限。
- 截图存在动态噪声：先冻结动画、时间、随机数据或加载状态；不能稳定时标记该区域无法可靠比较。
- 诊断结果冲突：保留各自证据，优先回到原始设计源；仍无法裁决时交给用户。

## 十、验证方案

为 Skill 建立场景化评估，不比较固定文案，至少覆盖：

1. 用户显式提供蓝湖链接：同时执行 MCP 结构核对与浏览器画面对比。
2. 用户显式提供图片：直接比较图片与实现截图，不虚构结构化蓝湖证据。
3. 当前消息无来源：从最新开发就绪任务文档自动找到设计材料。
4. 同时存在链接和图片且内容冲突：展示冲突，不静默选择。
5. 发现明显位置错误：修复后重新截图并由新诊断上下文确认。
6. 设计稿有按钮而需求禁止该行为：停止自动修改并请求裁决。
7. CSS 修复破坏交互：相关功能测试发现回归，流程不能声明完成。
8. 蓝湖 MCP 不可用但存在图片：降级为视觉路径并明确证据缺口。
9. 项目无法启动：不得仅凭代码判断设计还原完成。
10. 三轮后结论反复：停止循环并输出剩余问题。

全局失败条件包括：没有浏览器截图就声称完成；把视觉 Agent 的低置信度猜测当作确定缺陷；
静默改变业务行为；用开发阶段的自然语言设计摘要替代原始设计源；或把本流程结果写成最终验收通过。
