# Departure Handover 设计文档

## 文档状态

本文沉淀 2026-09-22 与用户的 brainstorming 讨论结论，供 `artifacts/skills/departure-handover/` 的实现使用。讨论以「一次一个问题」的形式逐项收敛，本文按最终决策整理，不逐句还原对话过程。

## 一、问题来源

用户即将离职，需要把自己名下的全部职责交接给接手人。真实痛点有三层：

1. **信息只存在脑子里**：权限账号、对接人、周期性职责、历史坑与隐性约定，在仓库里查不到，靠临时回忆必然遗漏。
2. **仓库里的线索可参考，但不能直接当事实**：提交信息不规范，仅凭 commit message 无法断定一个分支或一段改动在做什么；部分分支其实已被丢弃，从代码本身也看不出来。这不是否定某个仓库的线索价值——任何项目的提交记录、分支状态、代码注释都不可能百分百等于事实，所以线索一律先当参考，经人确认后才升格为结论。
3. **一次会话填不完**：全职责范围的信息量远超单次对话容量，需要跨会话增量推进，并且随时知道「还差什么」。

因此本 Skill 的核心机制是：**自动分析产出的是带证据的候选线索，由用户逐项确认后才进入正式交接内容**；账本跨会话增量维护，带覆盖度进度。

## 二、关键决策（逐项来自问答确认）

1. **交接范围 = 全职责**：在途任务 + 项目/代码知识 + 权限账号 + 对接人与关系 + 流程惯例（周期性职责）+ 隐性经验坑点。不裁剪成「只交代码」。
2. **完全独立的 Skill**，不依赖、不消费仓库内其他 Skill 的产出。用户明确指出 `project-familiarization-agent`（接手方视角）与 `development-readiness`（就绪与交接文档）产出的是**临时产物，事后可能被删除，且内容不一定准确**，因此不能作为本 Skill 的事实来源，也不建立自动联动。
3. **运行形态 = 先盘点、再跨会话逐项深挖**：首次会话产出「交接总账」把该交的东西全列出来，之后每次会话挑未完成项深挖成正式交接条目，全程显示覆盖度。
4. **落盘位置 = 工作仓库外的独立目录**（用户指定 `<handover-root>`）。理由：离职后可能失去工作仓库权限，且交接物最终由用户自己决定如何交付；同时避免污染工作仓库。
5. **完成判定 = 文档驱动**：用户把每项写清楚、自己确认无遗漏即算交完，**不引入接手人验收状态**，不依赖他人配合。
6. **产物结构 = 三层分离**（总账/候选池 + 分片条目文件 + 按需导出定稿）。理由：每次会话只读写少量小文件，跨会话增量安全；「线索」与「结论」物理隔离，贴合「先分析后确认」。被否决的方案：单文件内联账本（长文件跨会话反复编辑易改错位置、难局部刷新）、候选池+定稿两文件（定稿仍是越写越长的大文件，且访谈得来的非代码类项在候选池里没有落点）。
7. **账本是「人的账本」，不是「仓库的账本」**：一份账本覆盖用户名下全部职责，条目上标注所属项目。维护多个仓库时，对每个仓库分别跑分析、汇入同一份账本，不建多套账本。
8. **提交信息只作参考，不作结论依据**：分析优先采信相对客观的结构化信号（改动热区、改动时间、分支合并状态、blame 归属）；commit message 与代码注释可以作为线索呈现并附链接，帮助用户回忆，但不能用来断言「这个分支在做什么」。语义一律由用户确认。
9. **分支一律当候选，附客观证据再问人**：给出「最后提交时间 / 是否已合入主干 / 远端是否仍存在」三条事实，由用户判「保留移交 / 判废 / 需接手人继续」。Agent 不自行推断废弃。
10. **MCP（如云效）是可选增强**：会话内可用则拉取用户名下未关闭的需求/任务/缺陷作候选；不可用则跳过并在总账标注「该来源未取证」，不作硬依赖。
11. **敏感凭据零落盘**：账号密码、密钥、token、私钥不写入任何产物；`access` 类只登记权限项与移交路径。
12. **命名 = `departure-handover`**：描述场景（离职/离岗交接）而非一次性任务，符合仓库命名规范（小写英文 + 连字符）。
13. **Skill 定义与模板用英文撰写**：`SKILL.md`、`reference/`、模板、`README.md` 全部英文，状态值与证据标签也用英文标识符，符合仓库 English-first 原则。与用户对话时跟随用户语言；用户填入账本的内容用什么语言由用户决定，Skill 不做限制。

## 三、产物结构与状态机

```text
<handover-root>/
├── inventory.md                  # 总账：全部盘点项 + 状态 + 证据 + 覆盖度
├── items/
│   └── <分类>-<slug>.md          # 每个「要交」的项的深挖条目
└── export/
    └── handover-<YYYY-MM-DD>.md  # 按需拼出的可交付单文档
```

总账中每项的状态：

| 状态 | 含义 | 谁决定 |
| --- | --- | --- |
| `candidate` | 自动分析出的线索，未经用户确认 | Agent 写入 |
| `confirmed` | 用户确认这项要交，待深挖 | 用户 |
| `dropped` | 不用交（废弃分支、已下线、无人接），留一行原因**不删除** | 用户 |
| `written` | `items/` 下条目已成文、用户确认无遗漏 | 用户 |

设计要点：

- `dropped` 保留不删，目的是重跑分析时不再反复追问同一个废弃分支。
- 覆盖度 = `written ÷（总数 − dropped）`。每次会话开场先报覆盖度与「还差哪几项」。
- 状态默认单向推进，但用户可随时人工翻盘（例如把 `dropped` 改回 `confirmed`），Agent 服从用户判断。
- **内容的唯一源是 `items/` 条目文件**，总账只存状态与一行摘要，避免同一内容两处维护。总账与条目不一致时视为 bug，以用户确认为准修正总账。
- `<handover-root>` 由用户在首次会话指定。由于账本在工作仓库外、Agent 无法自行发现，**每次会话都需要用户给出该路径**；`inventory.md` 顶部固定记录 handover-root 的绝对路径与已纳入分析的工作仓库列表，便于用户自己回查与在新会话中提供。
- 条目文件名 `<分类>-<slug>.md`：slug 由用户确认时给出的短名生成（小写英文或拼音 + 连字符），冲突时追加短数字后缀；总账每项记录其条目文件名，slug 一旦落盘不再改名。

## 四、盘点分类

`items/` 文件名前缀即分类：

| 分类 | 覆盖内容 | 主要来源 |
| --- | --- | --- |
| `wip` | 在途工作：未完成的需求/任务/缺陷/线上问题，进度、下一步、卡点、截止压力 | 仓库线索 + MCP + 访谈 |
| `project` | 项目与代码知识：负责的仓库与模块、架构要点、启动与验证方式、高风险区、历史妥协 | 仓库线索 + 访谈 |
| `access` | 权限与账号：系统权限项、权限级别、移交与审批路径（**不含凭据内容**） | 访谈 |
| `people` | 对接人与关系：上下游联系人、谁依赖我、什么事找谁 | 访谈 |
| `routine` | 周期性职责：值班、例会、周期报表、定时任务、发布窗口 | 访谈 |
| `tacit` | 隐性经验与坑：一碰就炸的地方、只有我知道的约定、历史事故与规避手段 | 访谈 |

前两类能从仓库挖出线索，后四类基本只能靠结构化访谈抽取，两条路径分开设计。

## 五、自动分析规则（只产候选）

采信优先级从高到低——越靠后的信号越需要人确认：

1. `git log --author=<用户>` 聚合的改动热区：按目录与文件统计改动次数与最近改动时间。
2. 未合并的本地与远端分支、未合 PR：附「最后提交时间 / 是否已合入主干 / 远端是否仍存在」。
3. 用 blame 定位到用户名下的 `TODO` / `FIXME` / `HACK` / 临时 / 兼容 类注释。
4. `CODEOWNERS` 等归属线索。
5. commit message、注释文本、仓库文档描述：**仅作参考线索**附在候选项下供用户回忆，不用于断言语义。
6. 可选：MCP 拉取用户名下未关闭的需求/任务/缺陷。

证据标记（写入总账每一项）：

- `[confirmed]`：用户确认过。
- `[lead-git]` / `[lead-mcp]` / `[lead-file]`：有路径或链接依据的参考线索，未经用户确认。
- `[needs-confirmation]`：仓库里查不到，必须问用户。

硬约束：**不得把 lead 档直接升格成 `[confirmed]`**；用户确认是唯一的升格途径。

## 六、确认协议（批量过筛 + 逐项深挖）

1. **批量过筛**：分析完不逐条散问，按分类整批呈现候选清单（一条一行 + 证据），用户一次性批量判「确认 / 判废 / 拿不准」。每批默认不超过 10 条。
2. **拿不准的留在候选池**，下次会话再问，不强迫当场决定。
3. **逐项深挖**：只有 `confirmed` 的项才逐项追问细节，并写成 `items/` 条目文档。

访谈问题库（后四类问什么、前两类如何追问）下沉到 `reference/interview.md` 按需加载；取证命令与去重规则下沉到 `reference/analysis.md`。`SKILL.md` 保持精简内核 + 「何时读哪个 reference」的指针，与仓库既有 Skill 的渐进披露约定一致。

## 七、条目模板

一套共享骨架 + 按分类追加的小节，统一放在 `item-template.md`（不做六个模板文件，避免模板膨胀）。

共享骨架：

- 元信息：分类 / 所属项目 / 状态 / 接手人（可填「未定」）/ 最后更新
- 这是什么、为什么存在
- 当前状态
- 接手人要做的事（可执行步骤）
- 风险与坑
- 证据与入口（路径、分支、链接）
- 遗留待确认

分类专属小节举例：`wip` 补进度、下一步、卡点、截止压力；`project` 补模块边界、启动与验证方式、历史妥协的原因；`access` 补系统名、权限级别、移交审批路径、凭据现存位置的**指向**；`people` 补负责范围、什么事找他、他依赖我什么；`routine` 补触发时机与失败后果；`tacit` 补现象、原因、规避手段、「别去碰什么」。

## 八、跨会话续跑与幂等

会话固定开场动作：

1. 读 `inventory.md`。
2. 报覆盖度与「还差哪几项」。
3. 问用户本次要做哪一件：继续深挖 / 重跑分析找新线索 / 导出。

重跑分析严格增量：用稳定 key（分支名、文件路径、任务号）去重，只追加未见过的线索；`confirmed` / `dropped` / `written` 的项绝不被覆盖或回退。

## 九、导出

- 手动触发，产出 `export/handover-<YYYY-MM-DD>.md`。
- 只拼装 `written` 的条目，按分类成文；末尾附覆盖度与「尚未交完」清单，不隐藏未完成项。
- `candidate` / `dropped` 的内部内容不进导出版，保证对外版本干净。
- 导出物是派生物，可随时删除重建。
- 导出版默认只写事实与可执行信息，不含对人的评价；导出前请用户确认一遍。

## 十、边界与限制

1. 不修改工作仓库的任何代码或文档，只往用户指定的仓库外目录写。
2. 不读不写其他 Skill 的产出目录，不与之建立自动联动。
3. 不替用户判断某项该不该交，所有取舍以用户确认为准。
4. 不接管交接会、不发邮件、不代为通知他人。
5. 不保证穷尽：Agent 挖不到的只能靠访谈；只保证「挖到的都带证据、没挖到的明确标 `[needs-confirmation]`」。
6. 敏感凭据零落盘；用户口述凭据时拒绝写入并提示走密码库或 IT 流程。
7. 不引入接手人验收状态（本次明确不做）。
