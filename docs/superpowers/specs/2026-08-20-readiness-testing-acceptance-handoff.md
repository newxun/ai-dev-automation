# 开发就绪、测试与场景验收 Skill 交接文档

## 文档状态

本文沉淀 2026-08-20 的方案讨论，供后续设计和开发使用。它记录已经达成的方向、
必须满足的约束、建议的职责边界和仍待验证的决策。

本文不是三个 Skill 的最终实现规格。尤其是目录名称、模板字段和 Agent 调度方式，应在
检查现有资产及真实使用样本后再确定，不能把本文的示例直接机械实现。

## 一、问题与目标

目标用户首先是不熟悉当前项目的开发者，也可能是不熟悉项目技术栈、来自不同岗位的开发者；
长期目标是让不懂编程的参与者也能在 Agent 协助下完成目标确认、风险决策和结果验收。

当前最卡的不是编码过程，而是：

1. 开发前无法确认已有资料是否真实、当前环境是否可用、任务边界是否可靠。
2. 开发后缺少与原始需求和项目全局一致的测试及验收过程。
3. 常规代码 Review 只能判断实现质量，不能完整判断是否做对需求、是否越界以及是否引入
   全局回归。
4. 需求、听记、代码、技术栈说明和既有 baseline 都具有时效性，不能被永久当成当前事实。

因此，本次新增或重构的范围只包括：

- 开发就绪 Skill；
- 测试 Skill，包含按需浏览器测试；
- 场景验收 Skill。

开发实现和代码质量 Review 复用已有成熟 Skill，不在本次重新设计。

## 二、总体工作流

```text
开发就绪 Skill
    ↓
已有开发 Skill
    ↓
测试 Skill
    ↓
已有代码 Review Skill
    ↓
场景验收 Skill
```

测试和代码 Review 可以在条件允许时并行，但都必须在最终场景验收前形成结果。场景验收
消费它们的证据，不应把完整测试和代码 Review 再做一遍。

三个新 Skill 共享同一条材料链：

```text
原始资料
→ 项目全局认知与任务开发契约
→ 最终代码差异
→ 测试证据
→ 代码 Review 结果
→ 场景验收报告
```

任何摘要都不能成为封闭的信息终点。验收阶段必须能够回到原始需求、项目全局事实和实际
代码，而不是只核对开发就绪阶段生成的摘要。

## 三、共同设计原则

### 3.1 项目全局和任务局部必须同时存在

只关注任务容易局部正确、全局错误；只做项目介绍又无法指导具体开发。信息至少存在三种
作用域：

```text
工作区协作视角（仅多项目任务需要）
    ↓
项目全局视角
    ↓
具体任务视角
```

工作区根目录不等于全局视角。默认应将材料写入实际相关项目；只有用户明确要求工作区级
输出，或一个任务确实需要协调多个项目时，才增加工作区级索引或协调材料。

### 3.2 多任务是常态

一个项目可以同时存在多个开发中、暂停、待验收或已完成任务。不得设计唯一的
`current task`，也不得让一个任务的更新覆盖另一个任务。

每个任务需要独立且完整的材料、状态和历史。项目级事实可以复用，但任务必须明确自己基于
哪个版本或时间点的项目事实。

### 3.3 轻量不等于省略关键判断

第一版不引入复杂的 manifest、哈希同步系统、软链接或完整状态机。用户不应维护这些机制。
时效性先通过以下最小信息和关键节点复核解决：

- 资料采集或确认时间；
- 仓库、分支和 Commit；
- 关键来源及其位置；
- 结论的证据和失效条件；
- 开发开始前及验收开始前的变化检查。

只有真实失败案例证明这些机制不足时，再增加自动失效或细粒度版本能力。

### 3.4 能力差异必须被显式处理

不能默认接手者熟悉当前岗位、项目或技术栈。开发就绪阶段应了解或保守推定接手者的能力，
并调整交接深度：

- 熟悉技术栈但不熟悉项目：强调项目约定、业务和相似实现。
- 不熟悉技术栈：补充完成当前任务所需的最小技术路径、项目内范例和验证方法。
- 跨岗位接手：解释岗位间容易误判的边界和风险。
- 非技术参与者：突出目标、决策点、风险和可观察验收结果，把技术执行交给 Agent。

这不意味着生成通用教程。所有补充内容必须服务于当前项目和任务。

## 四、证据模型

### 4.1 结论类型

开发就绪中的实质性结论必须能够区分：

- **已验证事实**：由当前环境中的命令、测试或实际运行直接确认。
- **代码证据**：由当前代码、配置、依赖、CI、测试或 Git 历史支持，但尚未运行确认。
- **需求事实**：来自用户确认或本次采用的原始需求资料。
- **推断**：由证据推导但尚不能确认，必须说明推导过程。
- **决策**：本次任务主动采用的方案或边界，不得伪装成项目既有事实。
- **未知**：证据不足，当前无法可靠确定。
- **证据冲突**：来源之间不一致，必须展示冲突而不能静默选择。

现有 Development Readiness Skill 已有类似证据标签。开发时应优先兼容或演进已有模型，
避免无必要地建立第二套术语。

### 4.2 不同问题使用不同权威来源

判断当前实现时，可将以下顺序作为调查起点：

```text
当前环境的实际行为
→ 可执行配置、锁文件和 CI
→ 源码与测试
→ 近期 Git 变化
→ 项目文档与注释
→ 通用经验
```

这不是机械裁决规则，本地环境本身也可能配置错误。

判断目标行为时，优先依据：

```text
用户最新确认
→ 本次采用的原始需求
→ 历史需求或会议记录
→ 当前代码行为
```

代码可以证明“现在是什么”，不能单独证明“需求应该是什么”。

### 4.3 必须提供证据的结论

至少以下结论不能依赖 AI 直觉：

- 项目边界和项目归属；
- 实际使用的技术栈；
- 安装、启动、构建和测试方式；
- 项目全局约束；
- 任务相关代码入口和相似实现；
- 任务职责、修改范围和非目标；
- 验收标准和测试要求；
- 回归范围与高风险区域；
- 最终开发就绪结论。

引用证据时应尽量记录文件位置、命令与结果、运行环境、分支/Commit 和确认时间。无需给每个
普通描述添加引用，重点保证会影响开发决策的结论可追溯。

### 4.4 冲突与过期资料

项目文档、注释和历史 baseline 都是候选证据，不是天然事实。例如 README 声称使用 npm，
但锁文件、CI 和实际命令均使用 pnpm 时，应展示冲突并说明暂定判断。

不能为了输出完整报告而隐藏未知项，也不能把“看起来”“通常如此”等直觉改写成确定结论。

## 五、开发就绪 Skill

### 5.1 核心问题

开发就绪 Skill 回答：

> 对于当前接手者，在当前项目事实、任务资料和环境条件下，是否已经具备安全开始开发的
> 条件？

它不负责实现需求，也不替代后续开发、测试、代码 Review 或场景验收。

### 5.2 主要职责

1. 确认目标工作区、相关项目和可能的跨项目关系。
2. 收集并固化本次采用的需求、听记、任务说明和附件。
3. 建立与当前开发有关的项目全局认知，而不是无目标理解整个仓库。
4. 从依赖、配置、源码、CI 和运行结果确认项目实际使用的技术栈。
5. 根据接手者能力，补充当前任务需要的最小技术知识、项目内范例和注意事项。
6. 支持一个项目下的多个独立任务，不采用唯一当前任务模型。
7. 为每个任务明确目标、职责、边界、非目标、代码入口、影响面和已知风险。
8. 建立并验证足以开始开发的环境和最小开发路径。
9. 定义可验证的验收标准、测试要求和预期回归范围。
10. 给出就绪、有限就绪或未就绪结论，并列出证据、限制和下一步。

### 5.3 技术栈就绪

技术栈就绪不是罗列框架名称。它必须说明：

- 项目实实在在使用了什么，而不是仓库中偶然存在什么；
- 本任务会触及哪些技术和项目约定；
- 可以参考哪些项目内真实实现，以及参考边界；
- 如何启动、调试、测试和观察结果；
- 当前接手者在哪些方面可能不熟悉；
- 为完成本任务需要补齐的最小知识和高风险误区。

项目级技术栈事实应可复用，任务级内容只保留本任务相关的应用方式和能力缺口。技术栈材料
应允许作为独立文档存在，避免埋在庞大的任务报告中难以发现。

### 5.4 原始资料与历史

需求文档、任务来源、会议听记和用户提供的附件应归集到对应任务的 `raw` 逻辑区域，并由
任务材料引用。处理方式按来源区分：

- 用户直接提供且内容固定：保存本次采用的快照。
- 项目仓库中的权威文件：优先引用原路径，避免制造无意义副本。
- 外部且可能变化的来源：在安全和授权允许时保存快照，并记录原链接和采集时间。
- 敏感或不允许复制的材料：只记录安全引用和必要摘要，不能强行落盘。

新生成的任务材料必须完整，不能要求接手者先阅读历史版本才能理解。旧版本可进入该任务的
历史区域，用于比较和追溯，不应被静默覆盖。

### 5.5 文档落点约束

已经确认的约束：

- 默认生成在实际相关项目下，而不是工作区根目录。
- 多任务各自独立，不共享唯一当前任务文件。
- 项目全局材料与任务材料分层。
- 多项目任务可增加工作区级协调视角，但不能用它替代各项目材料。
- 新版本完整，历史版本用于追溯。

尚未确认的内容：

- 项目内根目录的最终名称；
- 文件命名规则；
- 状态是写入文件头、索引还是由目录表达；
- 项目级 baseline 与任务历史的具体版本策略。

开发前应先对照现有 Skill 的报告结构和真实产物，选择迁移方式。

### 5.6 输出状态

- **就绪**：开始当前任务所需的关键事实、环境、边界和验证路径已经得到足够证据支持。
- **有限就绪**：可以在明确范围内开发，但存在必须遵守的限制和残余风险。
- **未就绪**：存在会导致盲目实现、无法验证或产生不可接受风险的阻断。

状态由证据决定。不能因为用户希望继续或为了减少调查成本而虚报就绪。

## 六、测试 Skill

### 6.1 所处阶段

测试发生在开发完成后、最终验收前。测试负责产生可复现的行为证据，验收负责基于需求和
全局上下文判断这些证据是否足以接受交付。

### 6.2 主要职责

1. 读取开发契约中的验收标准、测试要求和回归范围。
2. 检查最终代码版本、测试环境和数据条件。
3. 根据修改类型选择最小充分的测试组合。
4. 运行现有单元、集成、接口或端到端测试。
5. 补充自动化测试未覆盖的必要功能验证。
6. 对 UI 或真实用户流程按需执行浏览器功能测试。
7. 仅在视觉风险存在时执行视觉检查或视觉回归。
8. 保存命令、步骤、环境、代码版本、结果和必要 artifacts。
9. 明确失败、跳过、无法执行和需要人工确认的项目。

测试 Skill 不给出最终场景验收结论，也不应未经授权修改业务代码来“顺手修复”测试失败。

### 6.3 浏览器功能测试与视觉测试

二者必须区分：

- **浏览器功能测试**：验证页面加载、输入、点击、路由、权限、请求、数据状态和用户流程。
- **视觉测试**：验证布局、样式、遮挡、溢出、响应式或截图差异。

出现以下条件时应考虑浏览器功能测试：

- 用户可见页面发生变化；
- 登录、表单、导航或完整业务流程受影响；
- 需要验证前后端集成；
- 验收标准包含交互行为；
- 其他自动化测试无法证明真实使用路径。

视觉测试仅在视觉需求或视觉回归风险存在时启用，不应成为所有任务的固定步骤。

### 6.4 成本控制

浏览器与视觉分析较耗上下文，应采用定向验证：

1. 从验收标准中提取少量关键用户路径。
2. 优先使用确定性脚本执行操作和断言。
3. 只在关键状态采集截图。
4. 正常路径保存简洁证据，失败后再深入分析。
5. 不默认逐帧分析视频或无目标自由浏览。

### 6.5 数据与安全

所谓“真实数据”不能默认等于生产数据。优先级应为：

1. 可复现的测试数据；
2. 测试或预发布环境中的代表性数据；
3. 经明确授权的生产只读抽查。

修改、删除、发送消息、支付、审批等具有业务副作用的操作必须有明确授权和隔离措施。
测试证据不得泄露凭据、个人信息或敏感业务数据。

### 6.6 输出

测试报告至少包含：

- 被测代码版本和工作树状态；
- 环境与数据前提；
- 验收标准到测试项的对应关系；
- 执行命令或可复现步骤；
- 通过、失败、跳过和无法验证的结果；
- 日志、截图等证据位置；
- 发现的问题和剩余测试缺口。

测试未通过或关键测试缺失时，应标记为场景验收阻断，而不是由测试 Skill 自行降低验收标准。

## 七、场景验收 Skill

### 7.1 核心问题

场景验收 Skill 回答：

> 最终交付是否满足本次真实需求、覆盖约定职责、没有未经确认的越界，并且在项目全局中
> 具备可接受的回归风险？

它不是另一套 Code Review，也不是测试执行器。

### 7.2 输入

至少读取：

- 本次采用的原始需求及相关听记；
- 项目全局 baseline 和技术栈事实；
- 任务开发契约；
- 最终代码差异；
- 测试报告与证据；
- 已有代码 Review Skill 的报告；
- 开发过程中确认过的需求、范围或设计变化。

若关键输入缺失、版本不一致或已经明显过期，必须先标记阻断或要求确认，不能假装完成验收。

### 7.3 综合检查链

场景验收应由一个主体保持完整推理链，避免把高度相关的视角拆成多个重复调查的 Agent：

```text
原始需求
→ 项目全局约束
→ 任务职责与边界
→ 实际代码修改
→ 测试和代码 Review 证据
→ 回归风险
→ 验收结论
```

具体检查：

1. **需求一致性**：是否采用正确需求版本，是否遗漏或误解。
2. **职责覆盖**：每项需求是否能映射到实际实现和验证证据。
3. **越界修改**：是否存在无需求依据的行为变化、重构或范围扩大。
4. **功能证据**：必要测试是否通过，测试环境和代码版本是否对应。
5. **代码质量**：消费现有 Review Skill 的结论，确认阻断问题是否处理。
6. **项目全局一致性**：是否破坏业务、架构、数据、权限或兼容边界。
7. **回归风险**：直接和间接影响是否得到足够验证。
8. **知识回流**：本次开发是否改变了项目事实，需要更新项目级 baseline。

建议形成如下追踪关系：

```text
需求 → 任务职责 → 实际修改 → 测试证据 → 验收结论
```

### 7.4 与代码 Review 的协作

默认只保留两个不同角色：

1. 现有代码 Review Skill：判断代码本身是否正确、可靠、可维护并符合项目规范。
2. 场景验收 Skill：综合需求、范围、全局影响、测试和 Review 证据作最终判断。

不建议为需求覆盖、越界、功能和回归分别创建固定 Agent，因为它们共享大量上下文且需要
连续判断。特殊安全、数据库迁移、性能或无障碍风险可按需调用专项能力，但不成为固定流程。

### 7.5 验收结论

- **通过**：必要需求、测试和质量门槛均满足，没有未处置的阻断风险。
- **有条件通过**：存在已明确、可接受且有责任人的限制或剩余风险。
- **需要修复**：实现、测试或代码质量存在明确缺陷。
- **需求待确认**：需求版本、业务口径或越界合理性无法自行裁决。
- **无法验收**：关键资料、环境或证据缺失，无法形成可靠判断。

报告应区分：

- 阻塞验收的问题；
- 需要修复但不阻塞的问题；
- 需要业务或用户决策的问题；
- 已验证通过的验收项；
- 无法验证的项目；
- 已被明确接受的剩余风险。

## 八、时效性与变化处理

原始资料和 baseline 都可能过时。第一版采用关键节点复核，而不是尝试维护永远实时的
baseline。

### 开发开始前

- 检查采用的原始需求是否有更新；
- 检查仓库相对记录 Commit 是否发生与任务相关的变化；
- 检查技术栈和关键开发路径是否仍成立；
- 只刷新受变化影响的结论。

### 验收开始前

- 确认最终验收使用的需求版本；
- 确认代码差异、测试报告和 Review 报告对应同一代码版本；
- 检查项目 baseline 后发生的相关变化；
- 检查开发过程中批准的范围变化是否已经进入任务契约。

发生实质变化时，保留旧版本用于追溯，并生成完整的新版本及简明变化说明。不能只输出一份
需要依赖旧文件才能读懂的增量补丁。

## 九、多项目与多任务

### 多任务

- 每个任务拥有独立任务材料、raw、测试证据和验收报告。
- 项目级 baseline 和技术栈事实可以共享。
- 并行任务影响相同模块时，需要提示冲突和基线漂移风险。
- 任务完成后不应因移动目录导致历史引用失效。

### 多项目

- 同一业务任务影响多个项目时，各项目保留自己的开发就绪和测试材料。
- 可增加一个工作区级协调材料，记录共同目标、项目间依赖和总体状态。
- 工作区材料不能替代项目内证据。
- 多项目任务的最终场景验收需要检查跨项目契约、版本组合和端到端证据。

## 十、边界与非目标

本次不做：

- 新的业务开发 Skill；
- 新的通用代码 Review Skill；
- 完整研发项目管理平台；
- 永久实时同步的知识库；
- 为每个检查维度固定创建独立 Agent；
- 不分任务风险地运行所有测试；
- 默认使用生产数据做破坏性验证；
- 让 AI 在证据不足时替代业务 Owner 作决定。

## 十一、开发前需要检查的现有资产

仓库已经存在 Development Readiness Skill、方法论、协议、报告模板和多份设计记录。后续开发
不能从空白重新实现，应先完成：

1. 对照本文逐项检查现有 Skill 已覆盖、部分覆盖和冲突的内容。
2. 检查真实运行产物，而不只检查设计文档。
3. 特别识别现有“工作区根目录报告”“会话级 baseline”“任务报告”“环境验证”和
   “UI 健康检查”规则如何迁移。
4. 保留已有可靠的授权、安全、证据冲突和环境验证协议。
5. 将开发后的完整测试职责从开发就绪中剥离；开发就绪只验证开始开发所需的最小路径。
6. 确认现有成熟代码 Review Skill 的输入输出，以便场景验收消费。

## 十二、建议开发顺序

1. 收集至少三类真实样本：陌生项目接手、多任务项目、UI 任务开发后验收。
2. 定义三个 Skill 共享的最小输入输出协议。
3. 修订开发就绪 Skill 的项目归属、多任务、技术栈就绪和证据要求。
4. 实现非浏览器测试主流程及标准证据输出。
5. 增加按需浏览器功能测试，再增加条件化视觉测试。
6. 实现场景验收 Skill，先消费现有代码 Review 报告，不重复实现代码 Review。
7. 使用端到端样本验证从 raw 到验收结论的完整追踪。
8. 根据真实失败案例决定是否增加更复杂的时效性或版本机制。

## 十三、首批评估场景

至少覆盖：

- README、配置、CI 和实际运行结果相互冲突。
- 项目使用真实技术栈，但接手者来自完全不同岗位。
- 同一项目同时有多个任务，且部分修改范围重叠。
- 工作区包含多个项目，但任务只属于其中一个。
- 一个任务确实跨越多个项目。
- 需求或 baseline 在开发期间发生变化。
- 开发实现满足任务摘要，却遗漏原始听记中的关键要求。
- 代码质量良好，但实现超出任务职责。
- 自动测试通过，但浏览器真实流程失败。
- 浏览器功能正常，但存在明显视觉回归。
- 测试使用了错误代码版本或不可复现数据。
- Code Review 和测试均通过，但修改破坏项目全局业务约束。
- 无法取得登录态、内部服务或必要测试数据。
- 任务只涉及后端逻辑，不应浪费成本启动浏览器。
- 非技术用户需要确认业务目标和剩余风险，但不应被迫理解实现细节。

每个场景应检查：

- 结论是否有可追溯证据；
- 是否准确保留未知和冲突；
- 是否在正确项目下生成材料；
- 是否支持多个独立任务；
- 是否只执行与风险匹配的测试；
- 是否把测试、代码 Review 和场景验收正确分层；
- 是否能够从原始需求追踪到最终验收结论；
- 是否在缺少关键证据时拒绝虚假通过。

## 十四、仍待决策

后续设计阶段需要明确，但本次讨论尚未形成结论：

1. 项目内文档根目录和最终文件命名。
2. 项目 baseline、技术栈文档和任务材料的具体拆分。
3. 任务状态、索引及历史版本的最小表达方式。
4. 外部资料快照的授权、安全和更新策略。
5. 测试 Skill 是单一 Skill 加按需 reference，还是包含独立浏览器测试子 Skill。
6. 测试报告与现有代码 Review 报告的标准接口。
7. 场景验收对“有条件通过”的授权和记录方式。
8. 面向非技术参与者的交互层与技术证据层如何分层呈现。

这些决策应依据现有 Skill、真实产物和使用成本作出，不能只凭目录美观或抽象完整性决定。
